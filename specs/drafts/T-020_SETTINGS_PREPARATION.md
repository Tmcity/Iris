# T-020 快捷键设置页前置设计记录

> 2026-10-03，Codex；T-017 仍在开发。本稿只定位后续设计依赖，未签发 T-020、未批准契约变更，也不要求当前开发提前实现。

## 1. 现有保存端口不包含快捷键编辑

当前 SettingsEditPlan 仅包含 GeneralSettingsPatch、TranslationChanges、TranslationOrder。T-020 不能为了增加快捷键页，绕过已验收的整窗保存而直接调用 ISettingsService.UpdateAsync 保存另一份草稿。

签发前需要通过 CCR 定义快捷键的增量编辑意图：按 Action 保留 base/target，未编辑项跟随提交时最新配置；与常规/服务草稿一次联合提交，外部同 Action 变更有明确冲突检测。具体声明待 T-017 实际接线验收后定稿，不在本稿增加 SettingsEditPlan 字段。

验收应包括：未失焦的录入框内容进入捕获计划、保存等待期间冻结、取消/关窗不写入、无关外部更新合并、同一绑定并发冲突、保存后的新草稿基线，以及混合页面只提交一次。

## 2. Backspace 清除与当前 Normalizer 冲突

ARCH §12.2 / N2 与 SettingsNormalizer.NormalizeHotkeys 目前会把有默认绑定的空白 Key 恢复为默认值；缺失的默认 Action 也会补回。因而不能简单从字典删除 InputTranslate，或保存 Key="" 后声称重启仍保持“清除”。

需在签发前明确用户看到的“清除”语义：

- 候选是保存明确禁用且无键的绑定，并经 CCR/规范修订使 Normalizer 允许该状态；启用前必须重新录入有效键。
- 另一方案是禁用并保留上次组合，但 UI 必须明确表达“禁用/保留”，不能把隐藏了文本当作已经清除。

两者不能在 UI、Core 编辑校验和 Normalizer 中各自选择。T-017 的 Enabled=false 无需校验 Key，只描述运行时注销，不能自动推出空白 Key 的持久化规则。

## 3. 草稿冲突、系统冲突与应用状态分开

录入页可以检测草稿内重复组合与既定非法组合；不能仅凭草稿校验宣称 RegisterHotKey 会成功。操作系统冲突以 T-017 的真实结果为准。

保存配置成功而原生注册失败时，不回滚已经提交的 General/Provider/Hotkey 混合事务，不显示“未保存”。App 应按本次目标绑定/代次显示实际应用结果；较新设置到达后不能继续显示旧代次成功。

现有 opaque SettingsApplyReceipt 用于 Core 的 Provider 发布/凭据清理，不能未经设计就混入原生热键注册状态。后续优先复用 T-017 App 协调器的实际状态，并明确 UI 持有、刷新与重试语义；是否需要新增 App 内部状态接口需等其实际实现。

## 4. 录入过程与全局快捷键竞争

录入当前已注册的组合时，WM_HOTKEY 可能先触发应用动作，抢走焦点。不能假设 WPF e.Handled 会阻止已注册的全局热键。

签发前需要研究录入期间的 App 内部暂停/恢复所有权：暂停哪些 Iris 注册、设置更新期间怎么合并、Escape/失焦/窗口销毁如何恢复、退出时不重新注册。不能把录入框销毁视为允许恢复一个旧绑定快照。

Win 修饰键、系统保留组合、IME 与普通键名解析不同；代码构造 KeyEventArgs 不证明物理键盘/Shell 行为。若需要新的临时原生拦截机制，必须先核查官方机制和边界，再单独批准，不能在 UI 中偷偷增加全局钩子。
