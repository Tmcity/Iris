## 3. R5-02：从创建进程到包装失败均持有完整清理责任

已复现两条实际 runner 路径：Start 返回 false 且 Dispose 抛错后，reader 返回 Failed，RetryCleanup 未再次 Dispose，资源责任丢失；包装失败后 child 已退出且 Process.Dispose 已调用，但 stderr 读任务仍在完成中，Read 与 Stop 均已返回。

1. 创建 Process/adapter 后立即有清理所有者。Start 未成功时不 Kill/等待一个不存在的 child，但 Process 对象/已取得流释放失败仍须记录可重试责任；删除启动前 Dispose 的空 catch。
2. 包装/管道初始化失败时，不能只 Kill、同步 Wait、Process.Dispose 后 throw 原包装异常。stderr drain Task、已取得流及 Process 都纳入同一个完整清理屏障。请求回执与 Stop 成功必须等待所有自有任务终态；流已 Close/Dispose 不等于异步读取 Task 已结束。
3. 即使 session 构造失败，也保留已取得的引用与阶段。CreateUnconfirmedSession 的降级不能静默把访问失败的资源当成已清理；状态需区分未启动、已启动未退出、已退出仍有流/任务、释放失败。
4. 仍使用现有进程对象/内部接口，不按名称/PID 清理，不新增公开 Core 契约。可以在现有内部 owner/启动异常模型中补充阶段，避免把未启动资源伪装成需要 Kill 的完整 session。
5. 失败尝试如在预算内无法真实结束，返回安全清理异常并保留 owner；不能 fire-and-forget、丢掉 stderr Task，或以成功 Stop 掩盖仍运行的资源。

## 2. 实施改动概述

### 2.1 R5-01：清理未完成必须报告清理异常
1. **严格区分“操作失败且已清理”与“仍有未完成清理”**：
   - 当启动进程失败且其自身 `Dispose()` 成功时，由于无残留物理会话和未释放句柄，`UiaSelectionReader` 安全返回普通 `UiaSelectionResult.CreateFailed(op.RequestId, "PROCESS_START_FAILED")`，不记录残留协调器责任，下一读取操作立即可接纳。
   - 当启动或包装失败且清理未能完整确认收尾时（例如 `process.Dispose()` 失败、`WaitForExit` 超时、`Kill` 异常），抛出 `ProcessStartupCleanupException`，包含未确认会话 `UnconfirmedSession`。
   - `UiaSelectionReader` 捕获 `ProcessStartupCleanupException` 后，将其登记至 `_failedCleanupCoordinator`，设置 `outcomeException = new IrisException(ErrorCode.CaptureFailed, "Child process startup cleanup failed and requires retry before new reads.")`。首轮读取明确抛出安全清理异常，决不伪装成普通的 `PROCESS_START_FAILED`。
2. **统一同步启动、异步启动、迟到启动错误的所有权与映射规则**：
   - 同步 `StartAsync` 抛出 `ProcessStartupCleanupException`、后台工作线程 `await startTask` 抛出 `ProcessStartupCleanupException`，以及握手超时/取消后的迟到启动 `delayedSession` 或其清理抛出异常，全部走同一所有权登记与异常抛出逻辑，统一抛出安全 `IrisException(ErrorCode.CaptureFailed)`，严禁被 `TimedOut` 或 `OperationCanceledException` 掩盖。
   - 登记后阻断后续所有新 `ReadAsync`（抛出 `CaptureFailed`），直至调用 `RetryCleanupAsync` 完成真实收尾。
3. **更正并扩充测试断言与验证**：
   - 更正 `ReadAsync_WhenRunnerThrowsProcessStartupCleanupException_BlocksNextRead_AndRecoversAfterRetryCleanup` 测试中首轮调用的断言，验证首轮抛出安全 `CaptureFailed` 异常、阻断第二轮读取，且在 `RetryCleanupAsync` 成功清理后恢复正常读取。

### 2.2 R5-02：从创建进程到包装失败持有完整清理责任
1. **未启动进程（`Start` 返回 false）资源持有与重试解耦**：
   - 在 `RealUiaProcessRunner.StartAsync` 中，若 `!started`，尝试立即 `process.Dispose()`。若 `process.Dispose()` 抛出异常，创建未启动会话 `CreateUnstartedSession(process)`（标记 `isUnstarted = true, hasExited = true`），抛出 `ProcessStartupCleanupException`。
   - `RealUiaProcessSession` 识别 `_isUnstarted`：`Kill()` 与 `WaitForExitAsync` 均为空操作安全返回，不调用无意义的 OS `Kill` 或等待不存在的 PID；`DoDisposeAsyncCore()` 仅重试未完成的 `_processDisposable.Dispose()`，实现可重试责任闭环。
2. **包装失败屏障覆盖 stderr drain Task、流及进程句柄**：
   - 在 `RealUiaProcessRunner.StartAsync` 中，包装失败进入 rollback 时，调用 `unconfirmedSession.Kill()`，并 `await unconfirmedSession.WaitForExitAsync(waitCts.Token)` 及 `await unconfirmedSession.DisposeAsync()`。
   - `WaitForExitAsync` 同时等待 OS 进程退出与 `_stderrDrainTask` 排空任务（在 1000ms 预算内通过 `_stderrDrainTask.WaitAsync(cancellationToken)`）。
   - 仅当 `cleanExit && cleanupEx == null && unconfirmedSession.IsFullyDisposed` 全部门闩确认时，才将原始包装异常抛出（此时为操作失败且已完全收尾）；若排空未结束、等待超时或释放异常，抛出 `ProcessStartupCleanupException(unconfirmedSession)`，将未收尾会话移交父级 reader 协调器。
3. **真实终态观察与任务等待**：
   - `RealUiaProcessSession.DisposeAsync()` 具备状态防重入与阶段记录：`_stdinDisposed`、`_stdoutDisposed`、`_stderrDrainObserved`、`_processDisposed` 独立记录已完成阶段，重试时绝不重复释放已关闭流与句柄。
   - 读任务收尾与 `StopAsync` 均完整等待 `stderrDrainTask` 终态，未完成前不宣称干净完成；放行后真实观察终态。
