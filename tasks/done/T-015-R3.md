## 2. TryShow 必须在真正提交 UI 状态时仍拥有发布资格（P1）

当前 TryShowAsync 只在 UI 回调开头检查 `_latestOperation`。EnsureWindowCreated、桌面查询、SourceInitialized/Show/Activate 等步骤会调用外部代码或产生重入；期间可接纳新意图。旧回调之后仍 ApplyRequest 并返回 true。

独立反例在旧 A 已开始 TryShow 的 GetMonitors 边界接纳 B，B 尚未 Show；A 已取消且不再是最新，却仍返回 true，并将 `obsolete-show` 写入输入框。

- 新意图接纳、caller Dispose、取消、隐藏/退出都必须使尚未提交的旧发布失效。窗口准备及可重入边界之后，提交正文/会话/焦点/可见性之前再次验证；不能只靠开头一次检查。
- 资格检查和最终接受有明确的提交顺序；不得通过在状态锁内 Show/Activate/调用外部依赖来阻止竞争。
- 已经产生的旧准备资源按真实所有者清理；不要在回滚旧 A 时误取消/隐藏已被 B 接管的窗口或覆盖 B 的内容。
- EndTryShow 不得在操作已经被隐藏/撤销后重新赋予 session 所有权。ApplyRequest 部分执行或抛出时也要按实际接管事实回滚，不能依赖调用返回后才设为 true 的 `appliedToVm` 标志断定“没修改”。
- 回归含：准备中接纳 B（B 未显示）、准备中 caller Dispose、创建/显示事件重入，以及正常发布对照；检查真实输入/可见性/返回值/引用，不能只测排队前作废。

## 3. 展示失败的状态必须反映真实窗口（P2）

独立反例：已有窗口可见，再次 TryShow 的原生定位返回 false。方法返回 false，但 catch 无条件将 `_isVisibleSnapshot=false`，实际窗口仍可见。

- 明确失败时保留既有窗口还是回滚隐藏，并执行对应动作；IsVisible / IsActive 必须与实际窗口一致，不能只改快照。
- 回滚需要的 ViewModel/WPF 状态操作在 UI 线程完成；旧发布失败不能改变较新操作的状态。
- 首次 Show 失败、已可见窗口更新失败、失败后再次成功发布、关闭失败保留重试入口分别验证。保留 R2 已修好的失败前不启动网络工作及副作用撤销规则。

## 4. 复制取消与 registration 注销必须真正退出后再释放（P1）

R2 已把复制取消改为 CancelAsync，但 TrackCopy / CancelPendingAndActiveCopies 丢弃返回 Task；待项立即 Dispose，实际写入结束也会 Dispose CTS，WaitForActiveWorkAsync 只等写入任务。独立闸门确认：取消回调仍挂起时，写入任务已经返回，drain 与 Presenter.Shutdown 均提前完成。

- 保存并观察在途和被替换待项的取消任务；回调退出、registration 注销、CTS 释放构成同一个完整所有者。仅写入 Task 完成或 token.IsCancellationRequested=true 不代表取消工作结束。
- callback 阻塞时 UI 仍响应，但 drain/Shutdown 不完成；异常使用安全诊断，释放闸门后所有工作自然退出。不要同步等待 UI 或重回锁内 Cancel。

## 三、三类核心问题修复与代码落地

### 3.1 TryShow 发布资格检查在提交 UI 状态时复核（P1）

#### 问题原因
在 R2 中，`TranslateWindowPresenter.TryShowAsync` 仅在 UI 调度入口检查了 `_latestOperation == op`。随后的 `desktopContext.GetMonitors()`、`EnsureWindowCreated`、`ApplyPlacement`、`Show` / `Activate` 等步骤会调用外部组件或引发 WPF 窗口事件重入。当旧操作 A 停留在准备阶段时，若外部同步或并发接纳了新意图 B（或调用方 Dispose A），旧回调 A 在完成窗口展示后未再次核验资格，仍盲目调用 `_viewModel.ApplyRequest` 将过期正文写入输入框并返回 `true`。

#### 修复落地
1. **状态锁二次复核**：
   在 `TranslateWindowPresenter.TryShowAsync` 的定位和窗口准备完成后、在调用 `_viewModel.ApplyRequest` 之前，再次加锁 `lock (_gate)` 检查发布资格：
   ```csharp
   if (_isShuttingDown || op.IsCallerDisposed || op.CancellationToken.IsCancellationRequested || !ReferenceEquals(_latestOperation, op))
   {
       hasNewer = !ReferenceEquals(_latestOperation, op) && _latestOperation != null;
       // 放弃向 ViewModel 提交
   }
   ```
2. **所有权防误杀与真实快照同步**：
   - 若被新意图 B 取代（`hasNewer == true`），旧 A 不向 ViewModel 提交正文，**不得**调用 `_window.Hide()`（避免误关已被 B 接管或正在使用的窗口），同步更新快照为真实窗口状态（`_isVisibleSnapshot = _window.IsVisible; _isActiveSnapshot = _window.IsActive;`），并返回 `false`；
   - 若因停机、调用方 Dispose 或取消而作废且无较新操作，则在 UI 线程上释放锁后调用 `_window.Hide()`；
3. **EndTryShow 与 AttachSession 所有权约束**：
   - `TranslateWindowOperation.EndTryShow(bool transferredWorkOwnership)`：仅当 `transferredWorkOwnership && !_isRetired && !_cts.IsCancellationRequested` 时赋予 `_hasSessionOwnership = true;`，否则赋 `false`；
   - `AttachSession()`：若操作已退休或已请求取消，返回 `false`，杜绝被撤销操作重获 session 所有权；
4. **ApplyRequest 异常安全回滚**：
   若 `_viewModel.ApplyRequest` 抛出异常，在 UI 线程捕获，撤销该操作 `RevokeOperation(op.Id)` 并在锁外完成回滚与隐藏。

### 3.2 展示失败状态与真实窗口一致（P2）

#### 问题原因
当窗口已在屏幕上可见时，若再次调用 `TryShowAsync` 且原生定位适配器返回 `false`（例如注入故障或窗口句柄异常），旧代码在 `catch` 块中无条件将 `_isVisibleSnapshot = false;`，但既有窗口并未被隐藏（`_window.IsVisible == true`），导致内部快照与真实窗口状态分离。

#### 修复落地
1. **真实可见性快照同步**：
   在 `TryShowAsync` 捕获准备失败后，记录发布前状态 `wasVisibleBefore`。若窗口原本已在屏幕上显示且更新失败，保留既有可见窗口；`_isVisibleSnapshot` 与 `_isActiveSnapshot` 严格同步为实际窗口属性：
   ```csharp
   _isVisibleSnapshot = _window != null && _window.IsVisible;
   _isActiveSnapshot = _window != null && _window.IsActive;
   ```
2. **锁外回滚与 UI 线程保证**：
   所有 WPF 窗口与 ViewModel 状态回滚操作必须在 UI 线程上执行，且 `_window.Hide()` 绝不在 `_gate` 锁内调用，避免发生 WPF 重入或死锁。

### 3.3 复制取消与 registration 注销尾部所有权完整观察（P1）

#### 问题原因
在 R2 中，`ViewModel.TrackCopy` 与 `CancelPendingAndActiveCopies` 调用了 `cts.CancelAsync()`，但未保存或观察返回的 Task；待办项被替换时立即 Dispose CTS；且 `WaitForActiveWorkAsync` 仅等待写入任务 `_currentCopyWriteTask`。当取消回调（callback）阻塞在受控闸门时，写入任务已先返回，导致 `WaitForActiveWorkAsync` 与 `Presenter.ShutdownAsync` 提前完成，取消回调尚未退出。
同类问题在 `TranslateWindowOperation.FinalizeRetire` 中也存在：使用 fire-and-forget `Task.Run` 注销 `_callerReg`，却立即归还 `_activeOperations` 名额并 Dispose CTS。

#### 修复落地
1. **取消任务保存与生命周期追踪**：
   - `TranslateWindowViewModel` 引入 `List<Task> _copyCancelTasks` 与 `HashSet<CancellationTokenSource> _cancelingCtsSet`；
   - 无论是待项被替换取消，还是 `CancelPendingAndActiveCopies` 触发的在途/待办取消，均通过 `RegisterCopyCancelTask` 登记 `AwaitCancelAndDisposeCtsAsync`；
   - `AwaitCancelAndDisposeCtsAsync` 在取消回调完全退出（`await cancelTask` 结束）后才 Dispose CTS；
   - `ProcessCopyQueueAsync` 的 `finally` 块仅在 CTS 未注册取消任务时直接 Dispose；若已被取消，交由取消任务在回调退出后释放；
2. **排空屏障完整等待**：
   - `ViewModel.WaitForActiveWorkAsync` 循环条件确保 `_copyCancelTasks.Count == 0`，必须等待所有取消回调彻底退出；
3. **Operation.FinalizeRetire 异步等待注销完成**：
   - `TranslateWindowOperation.FinalizeRetire` 调用 `_callerReg.DisposeAsync()`；
   - 若同步完成，则同步回收名额并释放 CTS；若异步挂起，启动 `CompleteRetireAsync`，等待注销任务真正完成后才调用 `_presenter.OnOperationRetired` 扣减活跃名额并释放 CTS。杜绝以“标记 retired”代替“资源清理完成”。

## 四、声明与更正

### 4.1 更正关于“CancelAsync 已调用即完整退出”的推论
在 R2 报告中，曾有推论认为“`CancelAsync` 已经由 await 驱动即代表取消工作退出”。此推论不严谨。调用 `CancelAsync()` 仅代表已向 CTS 派发异步取消信号；若取消回调本身挂起（例如在外部执行或受闸门阻塞），写入任务即使返回，取消回调及其关联注册仍未终止。
本工单彻底修正此推论，并在生产代码与测试中通过 Task 观察、`_copyCancelTasks` 与 `_callerReg.DisposeAsync()` 真正实现生命周期尾部的完整等待。

### 4.2 更正最近显示器并列规则声明
在 R2 报告中曾简略描述为“并列时选取首个显示器”。生产代码 `WindowPlacementHelper.FindNearestMonitor` 实际执行的并列决胜规则为：优先选取主显示器（`m.IsPrimary` 为 true）；若均为非主显示器，则按显示器设备名称字母序（`StringComparer.Ordinal.Compare(a.DeviceName, b.DeviceName) < 0`）选取。该逻辑与已批准规范保持完全一致，不改动已正确的算法，报告据此更正说明。
