## 2. R4-01：COM 获取结果尚未移交时的回滚

实际适配器 + 外部 COM/释放接缝已复现：GetSelection 取得一个 range 后，array 在 finally 释放失败，方法抛错、list 未返回，range 释放次数为 0；GetParent 取得 parent 后，walker finally 释放失败，parent 同样既未移交也未释放。element/pattern/range 的 Dispose 首次释放失败后重试仍只有一次 release 调用。类型获取失败的接缝用例也未回滚本次 COM 初始化。

1. GetSelection/GetParent 在方法成功返回之前，继续拥有全部刚取得的对象。辅助 array/walker 的释放失败会阻止移交，此时必须逐项回收已取得 ranges/parent；不能把 return 后执行的 finally 当成已移交成功。
2. 保留 body 与释放的错误信息（仅内部安全映射，不输出 provider 正文），某个释放失败不跳过其它对象；避免 array 在超限分支释放失败后被 finally 无条件重复处理、或清理错误覆盖原获取错误。返回成功与失败都要有明确所有权去向。
3. RealUiaElement/RealUiaTextPattern/RealUiaTextRange 不在调用 release 前标记 disposed。成功阶段不重复，失败保留剩余责任并允许同线程重试；保留已经修好的 RealUiaAutomationSession owner 检查与阶段状态。
4. CreateSession 的最终 IUIAutomation 类型获取/包装也纳入获取失败回滚：已取得 comObj 和本次成功 CoInitializeEx 必须成对释放。测试接缝返回不满足接口的对象时，不能在最后 cast 抛错后跳过回滚。该用例不代表真实正常 CoCreateInstance 会返回任意对象；它验证工单已要求的失败边界。
5. 使用已有真实适配器接缝补测：成功获取后 array/walker 释放抛错、获取和多个释放同时失败、各 wrapper 暂时失败后重试、初始化后类型获取失败。确认所有已取得对象逐项被尝试释放、无重复成功释放、最终返回安全失败且无文本。不得把适配器逻辑复制到 fake 中。

## 3. R4-02：真实 runner 的启动失败回滚仍须确认退出

此项为源码控制流缺口，不冒充已模拟的系统 Kill 拒绝：`RealUiaProcessRunner` 调用 `WaitForExit(1000)` 后未检查 bool，且回滚的 Kill/Wait/Dispose 错误仍空 catch；Process.Start 也处于回滚 try 之外。超时/拒绝退出时仍会丢掉实际自有进程责任，不满足 R3 原要求。

1. 初始化、Start 和会话构建均有明确资源所有者。没有启动的 Process 对象配对释放；成功启动后的包装/管道初始化失败，执行终止并检查真实退出结果。
2. Wait 超时/抛错或 Kill/Dispose 失败不能丢引用后只向父端返回普通 PROCESS_START_FAILED。以内部启动结果/异常或等效所有权模型把未完成清理纳入父端共享协调器；新 Read 阻断，Stop/Retry 可继续清理。公开 Core 契约不变。
3. 等待/回滚在后台执行，保持退出预算，不加长超时；清理失败安全可见，不包含原始异常/路径/协议内容，不枚举或结束其它进程。
4. 增加实际 runner 控制流的窄外部进程/构造接缝回归：Start 前失败、Start 后包装失败、Wait 返回 false、Kill/Wait 抛错、恢复后重试。可以替换外部进程调用，不得靠真实用户进程或伪造另一份启动状态机验证。

## 4. R4-03：finally 覆盖全部测试资源持有期

独立真实测试副本复现两条剩余路径：慢启动在 Start entered 后、进入新 try 之前注入异常，仍无法放行 startTcs；STA 测试在首次清理失败后、恢复 RefuseToExit 之前注入异常，其 finally 直接 Dispose，FakeTimeProvider 下的重试等待无法自行结束，并由清理异常覆盖主异常。

1. 慢启动测试的 try/finally 从实际可能持有启动任务之前开始，覆盖 entered 等待、时间推进、IsCompleted 断言、Busy 断言及后续操作。不能只把最后 Busy 断言放入 finally 保护。先放行实际 Start，再观察 read/stop/cleanup 终态。
2. STA 测试 finally 先解除本测试设置的拒绝退出、启动/流/任务门闩与虚拟时间等待，再 await/观察实际清理。保留 body 与 cleanup 两类异常；Join(5s) 与 IsAlive 断言不能替代回收已经启动的线程。
3. 同类新增测试（流释放、共享 Dispose、取消回调、尾流）检查整个自有资源持有期，统一补齐 finally 放行与真实任务等待。不得用空 catch、全局取消或延长等待掩盖遗留任务；不修改已验收翻译/热键生产范围。
4. 加入实际测试失败注入的终态验证，至少覆盖较早 Start entered 失败点和 STA 的失败重试点；证明原异常仍可见、所有自有任务/流/进程/线程结束。

# T-022B-R4 实施与验证报告

## 一、概述

本工单全面落实了 T-022B-R4 要求的全部三组缺陷修复与回归：
1. **R4-01（COM 对象移交与失败路径逐项回滚）**：`RealNativeUiaAdapter` 中 `GetSelection` 与 `GetParent` 在方法成功返回前保留对已获取 ranges/parent 的所有权，若辅助 `array` 或 `walker` 的释放抛错，逐项回收已取得的对象并聚合异常抛出；`RealUiaElement`/`RealUiaTextPattern`/`RealUiaTextRange` 不在 release 前标记 `_disposed = true`，失败允许同线程重试；`CreateSession` 类型转换与包装纳入 try-catch 保护，转换失败成对执行 COM 释放与 CoUninitialize。
2. **R4-02（真实 runner 启动失败回滚与退出确认）**：`RealUiaProcessRunner.StartAsync` 明确资源所有权，未启动的 `Process` 立即释放；包装失败调用 `Kill()` 后检查 `WaitForExit(1000)` 返回值；若未确认退出或 `Kill`/`Wait`/`Dispose` 抛错，通过 `ProcessStartupCleanupException` 将未确认退出会话纳入父端 `UiaSelectionReader` 的 `_failedCleanupCoordinator` 阻断后续读取并支持 `RetryCleanupAsync` 恢复。
3. **R4-03（finally 覆盖全部测试资源持有期）**：慢启动测试与 STA 调度测试的 `try/finally` 覆盖整个资源持有期，`finally` 优先解除拒绝退出与门闩并推进虚拟时间，完整保留主异常与清理异常并聚合抛出。新增针对早期 Start entered 失败点与 STA 失败重试点的回归测试。

公开 Core 契约、默认配置和中央包版本零修改。

### 10.3 启动失败的实际组合反例

探针目录 C:/Users/28910/AppData/Local/Temp/iris-t022b-r4-independent-review，Review.csproj 引用本次实际 Release DLL，使用既有 IVT 测试程序集身份。StartupReview.cs 的前四项经过实际 RealUiaProcessRunner 和实际 UiaSelectionReader，仅通过新 IProcessAdapter/流/包装 factory 接缝替换外部边界；最后一项使用实际 reader + 可控异步启动 Task，覆盖迟到失败。startup.log 原文，退出码 0：

```text
START_CLEANUP_waitFalse status=Failed errorCode=PROCESS_START_FAILED exception=none childAlive=True secondRead=IrisException
START_CLEANUP_killThrows status=Failed errorCode=PROCESS_START_FAILED exception=none childAlive=True secondRead=IrisException
START_DISPOSE_FAILURE status=Failed error=none retainedDisposeRetry=0 processReleased=False
START_ROLLBACK_DRAIN result=Failed childExited=True drainPending=True stopCompleted=True readEntered=True closeObserved=True
LATE_START_CLEANUP_FAILURE status=TimedOut exception=none childAlive=True disposeCount=0
```

具体安排和结论：

- waitFalse / killThrows：实际 runner 在包装失败后遇到未退出或终止故障，实际 reader 虽登记失败 coordinator、阻断下一次 Read，却将首次调用返回为普通 Failed / PROCESS_START_FAILED，没有清理异常，child 仍活着。这违反正式规范 §4；阻断第二次调用不能替代第一次正确报告。
- startDisposeFails：Start 返回 false 后 Dispose 抛错，runner 的空 catch 丢掉该失败责任；解除故障再调 Retry，Dispose 调用增量为 0，尚未释放。这里没有启动真实或 fake child，不应通过 Kill 一个未启动进程弥补。
- rollback drain：等待实际 stderr ReadAsync entered 后，让 session 包装失败，fake child 的物理退出与 Dispose 已发生；stderr 的 Close 已观察，但异步读取的完成门闩仍未放行。实际 Read 返回 Failed、Stop 成功，而 drain Task 未结束。该流替身模拟关闭与异步读取任务完成之间的时差，不声称操作系统永远不会结束读。外层 finally 才放行并 await 该自有任务。
- late failure：在 Start 已进入后用 FakeTimeProvider 推进 1600ms，再让实际启动 Task 以携带未退出 session 的 ProcessStartupCleanupException 结束。reader 返回 TimedOut，child 仍活着且未 Dispose。清理失败不能被较早发生的逻辑请求超时覆盖。

全部失败场景都使用外部 fake 进程/流，无真实系统 Kill 拒绝、无用户窗口查询。探针最后解除自己的故障、确认 fake 退出并等待 Retry/Dispose；不是遗弃资源来制造结果。
