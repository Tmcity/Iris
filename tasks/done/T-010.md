## 1. 背景

本工单用官方 `Anthropic` C# SDK 实现 Claude 翻译服务。**ARCH §9.2 已依据架构师对 SDK 12.50.0 的编译与本地服务器实测全部重写**，所有 API 名称与 SDK 行为都经过验证。标注“实测”的条目是观察到的事实，请照做，不要凭印象改写。

实测中发现几处 SDK 的“坑”，也是本工单的重点：

1. **SDK 会自动读取环境变量中的凭据与地址（安全问题）**。`AnthropicClient` 的 `ApiKey`、`AuthToken`、`BaseUrl` 三个属性，默认值分别取自环境变量 `ANTHROPIC_API_KEY`、`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_BASE_URL`。只设置 `ApiKey` 时，请求里仍会多出 `Authorization: Bearer {环境变量中的令牌}`；不设置 `BaseUrl` 时，请求会发往环境变量指定的地址。装了 Claude Code 的机器上这些变量很常见——**架构师和你的机器上都有**。后果是：用户配置了反代时，他本机的其他凭据会被发给反代服务器。**三个属性必须全部显式赋值，包括显式赋 null。**
2. **SDK 默认自带 2 次重试**，与 `iris.llm` 管道的重试叠加，一次请求最多会发出 6 次。必须设 `MaxRetries = 0`。
3. **流中途断开时，SDK 静默结束、不抛异常**，必须自己检查是否收到了 `stop_reason`。
4. **SDK 异常的 `Message` 原样包含服务端响应体**（反代可能在其中回显密钥），所以 SDK 异常不得作为 `innerException`，也不得写入日志。

另外，T-009 与本工单的 Provider 共享同一套超时、取消、异常归类与 TestAsync 逻辑。这部分逻辑细节很多、容易写错，本工单把它**抽取为公共骨架**，两个 Provider 共用，避免两份实现逐渐走样。

## 6. 实现要求

### 6.1 ProviderCallGuard（公共骨架）

把 T-009 中的超时、异常归类、TestAsync 逻辑抽取出来，形成下面三个方法（签名可以微调，语义不变；调整写进报告）：

```csharp
internal static partial class ProviderCallGuard
{
    /// <summary>
    /// 包装一次流式调用。创建 timeoutCts（timeout、timeProvider）并与调用方的 ct 链接；
    /// core 收到链接后的 token 与一个 resetTimeout 回调（每收到一个流事件调用一次，即 timeoutCts.CancelAfter(timeout)）。
    /// core 中抛出的任何异常都经过 Classify（顺序见 ARCH §9.1 “异常归类”）；mapSpecific 位于“已是 IrisException”之后、
    /// “HttpErrorMapper.TryMapException”之前，返回 null 表示不处理。
    /// 未配置等“调用前”检查由调用方在 core 之外完成。
    /// </summary>
    public static IAsyncEnumerable<TranslationChunk> GuardStreamAsync(
        Func<CancellationToken, Action, IAsyncEnumerable<TranslationChunk>> core,
        TimeSpan timeout,
        TimeProvider timeProvider,
        string providerId,
        Func<Exception, IrisException?>? mapSpecific,
        CancellationToken cancellationToken);

    /// <summary>非流式调用（模型列表等）：总超时，异常归类同上。</summary>
    public static Task<T> GuardAsync<T>(
        Func<CancellationToken, Task<T>> call,
        TimeSpan timeout,
        TimeProvider timeProvider,
        string providerId,
        Func<Exception, IrisException?>? mapSpecific,
        CancellationToken cancellationToken);

    /// <summary>ARCH §9.1 的 TestAsync 语义。</summary>
    public static Task<ProviderTestResult> RunTestAsync(
        ITranslationProvider provider,
        string targetLanguage,
        TimeProvider timeProvider,
        ILogger logger,
        CancellationToken cancellationToken);
}
```
- 用它重构 `OpenAICompatibleTranslationProvider`：`TranslateStreamAsync`、`ListModelsAsync`、`TestAsync` 都改为调用这三个方法，Provider 内不再有自己的 `ClassifyException`。
- **重构的安全网**：T-009 的全部 Provider 测试必须**不加修改地**继续通过（第 6.5 节 C9-6 要求修改的除外）。报告中贴出重构前后 `OpenAICompatibleTranslationProviderTests` 的测试数与通过数。
- `RunTestAsync` 的 Warning 日志**只写异常类型名，不传入异常对象**（ARCH §9.1 已更新；异常消息可能包含服务端响应体）。

### 6.5 T-009 评审遗留

- **C9-1**（ARCH §9.1 已更新）：2xx 响应既不是事件流、也一个 SSE 事件都没收到时（例如网关返回 200 的 HTML 页面），`Detail` 改为 `"服务未返回事件流（Content-Type: {媒体类型或“无”}），请检查 BaseUrl"`。架构师实测：目前这种情况的提示是“响应流意外结束”，会误导用户以为是网络问题。
- **C9-2**（ARCH §9.1 已更新）：`Usage` 目前要求 prompt 与 completion 两项都存在，否则整体为 null；改为任一项存在即构造 `TokenUsage`，缺失项为 null（流式与非流式两处）。
- **C9-3**（ARCH §9.1 已更新）：`TestAsync` 的 Unknown 结果带上 `ProviderId`；Warning 日志不再传入异常对象。（由 6.1 的 `RunTestAsync` 统一实现。）
- **C9-4**（简化）：流式循环中先用四个字符串比较判断“需要立即抛出的 finish_reason”，再调用 `MapFinishReason` 只为了让它抛异常，逻辑重复。改为：收到非空 `finish_reason` 时直接调用 `MapFinishReason`（错误类取值在其中抛出），并保存返回值供最后一个 Chunk 使用。
- **C9-5**（简化）：`ExtraHeaders` 与 `Authorization` 的添加逻辑在 `TranslateStreamCoreAsync` 与 `ListModelsAsync` 中各写了一遍，提取为一个私有方法 `ApplyHeaders(HttpRequestMessage)`。
- **C9-6**（测试）：
  1. 工单 7.3 第 26 条要求覆盖三种取消时机（发请求前、等待响应头时、读流时），目前缺少“等待响应头时”。用 `DelayingHandler` 补上。
  2. 无进展超时的成功用例（AC-4 第一个用例）目前只断言 `results.Count > 0`，改为断言恰好是 `chunk0`～`chunk4` 五个 Delta 加最后一个 Completed Chunk。
  3. 几个流式测试用 `await Task.Delay(50)` 等待 Provider 消费事件后再推进虚拟时间。这在机器繁忙时可能来不及消费，从而误报超时。给 `ControllableStream` 增加一个信号（例如“有读取正在等待数据”时完成的 `Task`），测试改为等待这个信号，不再依赖真实时间。

## 3. 与工单的偏差与 SDK 实测发现

1. **SSE `ping` 心跳事件被 SDK 12.50.0 内部静默吸收**：
   实测 Anthropic C# SDK 12.50.0 的 `RawMessageStreamEvent` 仅包含 6 种消息事件类型（`Start`、`Delta`、`Stop`、`ContentBlockStart`、`ContentBlockDelta`、`ContentBlockStop`），并不包含 `Ping` 类型。当 SSE 传输层接收到 `event: ping` 时，SDK 内部的解析器将其丢弃并直接拉取下一条事件，不会通过 `CreateStreaming` 向外产出任何事件。
   为了严格兑现 ARCH §9.2 规定的“每收到一个流事件（包括 ping）都重置无进展超时计时”，`AnthropicTranslationProvider` 通过轻量封装 `HttpClient` 响应流（`ProgressTrackingHandler` 与 `ProgressTrackingStream`），在底层响应流每次成功读取网络数据字节时即刻调用 `resetTimeout`，既真实实现了长文本翻译中的心跳保活防超时，又与官方 SDK 的静默机制无缝兼容。为防止底层 `HttpClient` 因报文被二次发送而抛出 `InvalidOperationException: The request message was already sent`，handler 在转发前对 `HttpRequestMessage` 执行浅克隆。
2. **`BetaFallbackBlock` 的结构**：
   在 SDK 12.50.0 中，`BetaFallbackBlock` 的属性为 `From`（类型为 `BetaFallbackInfo`，模型通过 `From.Model.Raw()` 读取）、`To`（类型为 `BetaFallbackInfo`，模型通过 `To.Model.Raw()` 读取）、`Trigger`（`BetaFallbackRefusalTrigger`）与 `Type`。在流处理时对 `fallback` 内容块予以忽略，由回退模型接着产出文本块。
3. **`ErrorType` 枚举成员与 413 映射**：
   SDK 12.50.0 的 `Anthropic.Models.ErrorType` 枚举定义了 9 个成员（`InvalidRequestError`、`AuthenticationError`、`PermissionError`、`NotFoundError`、`RateLimitError`、`TimeoutError`、`OverloadedError`、`ApiError`、`BillingError`），不包含 `RequestTooLarge`。当服务端返回 413 时，在 JSON 错误响应中其 `type` 字段为 `"request_too_large"`，Provider 在捕获 SSE 错误或 API 异常时，通过 JSON 内容与等效状态码判定为 413，映射至 `ErrorCode.InputTooLong`。
4. **模型列表分页 API**：
   SDK 的 `client.Models.List(cancellationToken)` 返回 `ModelListPage`，其数据列表属性为 `Items`（每一项为 `ModelInfo`，模型 Id 为 `item.ID`），分页判断为 `page.HasNext()`，翻页调用为 `await page.Next(cancellationToken)`。
5. **`MessageCreateParams.System` 类型**：
   SDK 的 `System` 属性类型为 `MessageCreateParamsSystem`（Beta 下为 `Beta.MessageCreateParamsSystem`），属于 init-only 且支持隐式转换，在构建参数时显式强转 `(MessageCreateParamsSystem)rendered.System`。
6. **`AnthropicTranslationProvider` 实现 `IDisposable`**：
   因为 Provider 持有私有 `AnthropicClient`（内部含有 `HttpClient`），为满足代码分析规则 CA1001，`AnthropicTranslationProvider` 实现了 `IDisposable`，在 `Dispose()` 中释放 `_client`。
7. **`ControllableStream` 防死锁超时保护**：
   测试辅助类 `ControllableStream.WaitForReadAsync` 中引入了 5 秒安全超时保护（`WaitAsync(TimeSpan.FromSeconds(5))`），若流式消费异常终止，测试能快速失败并定位根因，防止进程永久阻塞挂起。
