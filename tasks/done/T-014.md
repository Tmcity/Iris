## 2. 必须遵守的行为

完整语义以 ARCH §6.1 为准，特别注意：

1. 构造时一次索引实际注册项；允许空/部分集合；重复、null 项、非法枚举在构造时拒绝，异常不格式化注册对象。
2. 调用入口先处理已取消；非取消调用的 null context/非法 Action 以 Error 级 InvalidArgument 默认文案结束；有效但未注册动作以 Warning 级固定“该功能尚未开放”提示结束。不调用 Handler/不排队。
3. 在任何 UI 排队/await 之前原子取得动作执行权；同动作重复和三个截图动作之间冲突均立即忽略。不得全局串行化其它动作，不得让被忽略调用等待或取消原调用。
4. UI 回调真正开始前再次检查取消；Handler 在目标 UI 线程启动。完整等待 Handler 返回的 Task，包括同步抛错、异步抛错、取消和清理；不能只 await DispatcherOperation 的外层 Task。
5. 调度排队期间和 Handler 挂起期间都占用执行权；任何退出在 finally 释放。Handler 不配合取消时仍等待实际退出，禁止通过取消等待提前放行下一次同动作。
6. 没有 Application 时构造/Host.Build 仍成功；实际调度才报告安全错误。Dispatcher shutdown/排队中止与 OCE 静默；未关闭时的调度异常按未知错误处理。不得使用 Dispatcher.CurrentDispatcher 自动创建调用方线程的 Dispatcher。
7. 已知异常按 ErrorCode 默认文案通知，未知异常按 Unknown 默认文案通知，级别 Error。通知标题/未开放提示放入 App 资源，其它错误文案复用 ErrorMessages。日志只记安全元数据；Payload、原始异常对象及其消息/详情/内部异常不得进入日志或通知。
8. 通知服务失败时只安全记日志，不递归提示；执行权仍释放。业务取消不提示错误。无需改动既有 GlobalExceptionHandler 或 TrayNotificationService。

## 3. 验收与有区分力的测试

使用受控门闩/排队适配器，不以任意 Task.Delay 假设交错已经发生。等待有超时，测试失败时用 finally 放开门闩并关闭/等待自己创建的 STA 线程；不得遗留后台线程或挂起任务。

| 场景 | 必须证明的结果 |
|---|---|
| 空/部分注册，重复/非法/null 注册 | 实际 Host 能构建和解析单例；合法部分集合可用；错误注册被拒绝 |
| 同 Action 多线程触发，第一次尚未进入 UI | 只排队一次；重复调用立即完成，无通知、无第二次 Handler |
| Handler 首次 await 后挂起 | 原 DispatchAsync 未完成；执行权未提前释放；放行并完成后同动作可再次执行 |
| 截图三动作的不同组合 | 对三个成员均覆盖占用/冲突，冲突不入队；释放后其它截图动作可执行 |
| 两个不同非截图动作，截图与非截图动作 | 可以同时处于异步执行中，没有不必要的全局互斥 |
| 入口已取消 / UI 排队后取消 | Handler 不启动，无错误通知，原调用结束后可再次触发 |
| Handler 忽略已取消令牌并等门闩 | 令牌原样传入；Dispatch 和执行权等到实际退出；重复调用仍被忽略 |
| 同步/异步 IrisException、未知异常、OCE | 分别得到默认已知文案、Unknown、静默；下一次调用均能执行 |
| 假 Payload/异常 Message、Detail、Data、InnerException 带假凭据 | 捕获日志状态、Exception 参数和通知，不能包含这些测试标记；禁止用真实凭据 |
| 通知服务抛异常 / 调度器抛异常 | 不递归通知；调用不遗留执行权；后续调用成功 |
| 真实 WPF Dispatcher 的后台和 UI 线程调用 | 由独立 STA Dispatcher 消息循环运行实际适配器；断言 Handler 开始时线程 ID/CheckAccess 正确，内部 Task 仍被等待 |
| 真实 Dispatcher 关闭 / 解析器返回 null | 关闭静默；缺少 Dispatcher 按未知调度失败处理；均有界结束并释放执行权 |

假调度器用于建立竞态，不能替代最后两项对生产 WPF 适配器的验证。测试不创建可见窗口，不操作用户桌面/剪贴板，不真实联网。沿用架构测试确认契约注释同步、依赖方向和包白名单；不增加 NuGet 包。

## 2. 核心设计与关键机制说明

### 2.1 受控门闩如何建立 UI 排队与异步执行交错
在 `ActionDispatcherTests.cs` 中，绝不依赖无把握的 `Task.Delay`，而是通过严格的配对门闩（`TaskCompletionSource`）与可拦截的调度替身建立精确交错：
1. **尚未进入 UI 时的并发重入（场景 2）**：
   - 使用 `ControllableUiDispatcher` 拦截 `InvokeAsync`，在调用入队时通过 `queueEntered.TrySetResult()` 确认已进入调度排队，并 `await proceedUi.Task` 挂起；
   - 此时在另一线程并发调用同一动作，立即返回已成功完成的 `Task`（未被阻塞），执行次数仍为 0；
   - 随后设置 `proceedUi.TrySetResult()` 放行第一个调用，Handler 执行一次且无异常通知。
2. **首次 await 挂起与释放（场景 3）**：
   - Handler 内部通过 `handlerStarted.TrySetResult()` 确认已进入并在首次 await 前触发，随后 `await handlerResume.Task`；
   - 断言原 `DispatchAsync` 此时处于未完成状态；再次触发同动作立即被忽略返回已完成任务；
   - 放行 `handlerResume` 后，原调用完成，再次触发同动作可正常启动并完成第二次执行。
3. **取消令牌与 Stubborn Handler（场景 7）**：
   - Handler 启动后捕获 `CancellationToken`，外部调用 `cts.Cancel()` 触发取消；
   - Handler 故意不配合退出，而是等待门闩 `await latch.Task`；
   - 验证 `DispatchAsync` 在门闩放开前绝不提前完成，同动作的并发重入调用依旧被忽略；门闩放开后原调用静默结束，后续调用恢复可用。

### 2.2 真实 STA Dispatcher 测试的创建与安全退出机制
在场景 11 和场景 12 中，为验证真正的 WPF `Dispatcher` 适配逻辑：
1. **独立 STA 消息循环创建**：
   - 测试启动专用 `Thread`，显式设置 `SetApartmentState(ApartmentState.STA)` 和 `IsBackground = true`；
   - 线程内初始化 `DispatcherSynchronizationContext`，并通过 `TaskCompletionSource` 确保 `Dispatcher.CurrentDispatcher` 就绪后再由 `Dispatcher.Run()` 启动真实消息循环。
2. **安全退出与无遗留守护**：
   - 测试主体包裹于严格的 `try ... finally` 块中；
   - 在 `finally` 中检查 `if (staDispatcher != null && !staDispatcher.HasShutdownStarted) staDispatcher.InvokeShutdown();`；
   - 紧接着通过 `staThread.Join(5000)` 等待线程完全退出并释放，确保不遗留任何活动后台线程、悬挂任务或死锁。

### 2.3 安全日志与凭据防护
- `ActionDispatcher` 使用结构化 `[LoggerMessage]` 源生成器；
- 日志只输出 `Action`、`Trigger`、`ErrorCode` 和 `ExceptionType` 字符串；
- **严禁**将 `Exception` 对象作为日志异常参数传递（避免打印栈中附带的内部异常与属性）；
- 原始异常的 `Message`、`Detail`、`Data`、`InnerException` 以及 `ActionContext.Payload` 严禁出现在任何日志、异常参数或通知消息中；
- 单元测试（场景 9）构造带假凭据的异常链与 Payload，穷举断言所有日志条目和通知，确认无任何标记泄漏。
