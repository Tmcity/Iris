## 1. 只修一个剩余分支

R5 的完整 Session 失败保留、创建/排队期间关停以及 Host 并发退出已独立通过；原业务保存、查询、主题、路径、日志及这些已修复流程保持不变。

本单仅完成 R5 原要求中“尚未组装 Session 的局部回滚”部分。当前 SettingsWindowPresenter.ShowCoreAsync 的 session==null 分支，在 Close 取消时只检查 HWND：有 HWND 就抛错并丢失局部 window/scope 的管理入口；没有 HWND 就直接 Dispose scope，即使窗口仍未关闭。

## 2. 修复要求

- 创建尝试从取得 scope/window 起就有可追踪的资源所有者，即使 VM/完整 Session 解析失败也不能丢失。采用 App 内部小型创建/回滚状态即可，不新增公共契约或全局任务框架。
- 局部回滚失败时保留这些资源及重试入口；后续 Presenter.ShutdownAsync 必须处理它，持续失败就向调用方报告失败，不得因 _activeSession 为空而报告全部清理成功。
- 不以 HWND==0 判断 Window 已关闭：尚未显示、尚未创建 HWND 的 Window 也可能取消 Close。使用真实关闭完成状态确认后，才允许释放其 scope 和解除所有权。
- 解除 Closing 取消/故障后，重试通过同一 Presenter 完成该次窗口关闭与 scope 释放一次。清理未结束前，新 Show 不得覆盖待清理资源或制造另一个孤儿窗口。
- 如果局部创建已经启动了异步工作，仍按已有协议停止接纳并观察退出，再释放依赖；不能用吞异常、删除 Dispose 或抛完异常就丢弃引用代替清理。
- 不为失败路径临时补造正常 SettingsViewModel/Session 并启动额外查询，不改配置、Normalizer、公开接口，也不重写已通过的正常会话流程。

## 3. 受控回归

直接调用实际 Presenter，真实 WPF Dispatcher 与 DI scope，后续 ViewModel 解析注入失败，窗口 Closing 取消回滚。覆盖两种窗口状态：已创建 HWND、从未创建 HWND。

故障存在时，断言窗口仍存活且 scope 未释放，Presenter 保留清理责任，Shutdown 不成功；解除取消后再次 Shutdown，断言窗口从 Application.Windows 移除、HWND 不再存活、scope 释放一次。另保留没有 Closing 取消的正常失败回滚，以防新增状态导致资源反而不释放。

不能只断言“抛出了异常/没有 Dispose”，也不能仅在测试 finally 手动清理后声称生产重试成功。finally 仍要作为测试兜底回收自有窗口/资源，以免失败用例污染后续测试。

# T-018-R6 实施报告

## 1. 修复概述

针对 T-018-R5 遗留的“Session 尚未组装时，回滚关闭被取消会导致窗口遗留、丢失清理入口，且无 HWND 时会错误释放 scope”问题，在 `SettingsWindowPresenter` 中完成以下修复：

1. **资源所有权从创建初期建立（`PartialWindowCleanup`）**：
   - 在 `SettingsWindowPresenter` 内部定义私有结构/嵌套类 `PartialWindowCleanup`，在创建尝试开始（`CreateScope()` 和获取 `window`）时立即接管 `scope`、`window`、`saveCoordinator` 与 `viewModel` 的生命周期跟踪。
   - `ShowCoreAsync` 中从取得 `scope` 起即通过互斥锁 `_gate` 暂存至 `_pendingRollback`。即使后续 ViewModel 或主题服务解析失败，资源也不会遗失所有权。
2. **严谨的窗口关闭判定，消除 HWND==0 误判**：
   - 彻底废除仅依赖 `HWND == IntPtr.Zero` 作为关闭依据的逻辑。在 `PartialWindowCleanup.CleanupAsync` 中挂载 `window.Closed` 事件监听，并核对 `Application.Current.Windows` 集合是否仍包含该窗口，以及原生 HWND 是否有效。
   - 若 `Closing` 被取消导致窗口未真实关闭（`!closedFired`），绝不释放 `scope`，并抛出 `InvalidOperationException`，保持资源存活。
3. **Presenter.ShutdownAsync 纳入局部回滚清理责任**：
   - `Presenter.ShutdownAsync` 的准入条件扩展为 `_activeSession == null && _pendingRollback == null && (_openTask == null || _openTask.IsCompleted)`；当 `_pendingRollback` 存在时必须进入 `ShutdownCoreAsync` 进行清理。
   - 若局部回滚清理失败（如窗口关闭继续被取消），向调用方汇报异常，绝不因 `_activeSession == null` 虚假报告清理成功。
   - 故障解除后，再次调用 `ShutdownAsync` 成功触发 `PartialWindowCleanup.CleanupAsync`，完成窗口关闭与 `scope.Dispose()` 释放一次，并清理 `_pendingRollback`。
4. **清理未结束前，新 Show 拒绝覆盖**：
   - 新调用 `ShowCoreAsync` 时首先检查并尝试清理遗留的 `_pendingRollback`；若旧清理仍失败则抛出异常，绝不覆盖未清理资源或制造孤儿窗口。
5. **保留无取消时的正常失败回滚**：
   - 当 ViewModel 解析失败但窗口关闭未被取消时，正常关闭窗口并排干已启动的异步工作，释放 `scope.Dispose()`，不泄漏任何资源。
