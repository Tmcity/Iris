## 2. 隐藏与 VM 重入不能被旧发布覆盖（P1）

独立实际 Presenter/Window 反例：

1. A 在 GetMonitors 准备边界调用 HideAsync，`_latestOperation` 被清为 null；A 随后继续 Show。第二次资格检查虽拒绝 A，却把 null 也判成 hasNewer，留下可见窗口。最终 `accepted=false`，但快照和实际窗口都为可见。
2. A 的 ApplyRequest 写 InputText 并触发 PropertyChanged；该通知中 B 通过公开端口成功发布。A 恢复后继续执行 ApplyRequest，取消并 Detach B，把 `_activeOperation` 改回 A。B 的正文仍在，但 B 不再是有效会话且已取消。

要求：

- 区分没有最新意图（隐藏/退出）与确有较新意图；存在较新意图也不等同它已经接管实际窗口。旧操作的准备动作不能在 Hide 已生效后重开窗口，更不能回滚已由较新操作接管的窗口。
- 发布提交必须涵盖实际 ViewModel 状态变更及其同步通知产生的重入。只在 ApplyRequest 前检查一次，或最后把 accepted 改 false，都不能修复已经误取消 B 的副作用。
- 可以采用内部状态先一致提交、再通知，并对重入后续步骤校验操作/代次的方式；不强制具体实现。不得在状态锁内 Show/Activate 或调用可重入的外部代码。
- 操作取消、session 赋予/释放、原始输入/复制资格等变更只作用于所属操作；旧 A 的 continuation/finally 不能取消或替换 B。
- EndTryShow 与异常回滚保持真实持有，不复活失效 session、不清理较新操作。成功及失败的可见/激活快照均来自真实窗口，不能用 FocusInput 参数代替实际 IsActive。
- 回归必须含准备中 Hide、准备中退出/Dispose、PropertyChanged 中新 B 真正发布、通知中 Hide 以及普通发布对照；检查当前 ActiveOperation、B 的取消状态、输入/卡片、真实窗口及返回值。

## 3. CTS 同时等待写入与取消结束（P1）

R3 已等待取消回调，但 `AwaitCancelAndDisposeCtsAsync` 在取消任务结束就 Dispose CTS，没有等待该 CTS 对应的在途 SetTextAsync。反向时序仍失败：取消回调先结束、写入尚未返回时，当前传给 IClipboardService 的 token.WaitHandle 已抛 ObjectDisposedException。

- CTS 的最终释放必须同时满足对应写入真正返回、取消回调/注销收尾完成；待项从未启动写入时也要通过明确所有者完成取消及释放。取消完成不是写入完成，写入完成也不是取消完成。
- 保持两种先后顺序都正确：写入先返回/取消后退出；取消先退出/写入后返回。副作用已越过提交点时仍观察真正返回，不能因取消而提前释放资源。
- 用单一完整所有者登记取消/写入状态，登记完成后才运行外部取消动作，不在 `_cancelingCtsSet` 与任务列表交接之间留下 drain 可误判空闲的空档。
- 避免同一 CTS 重复登记取消/释放；操作替换、隐藏、退出和复制循环 finally 都通过同一收尾路径。不新增无界取消任务，不重新引入 UI/锁内同步等待。
- 所有成功/失败/取消组合完成后 drain/Shutdown 都退出，计数归零，CTS 只在最后释放。原有复制单在途/单最新待办、取消异常安全日志保持。

# T-015-R4 完成报告

## 一、概述

本轮开发严格落实工单 `T-015-R4` 的所有要求，彻底修复了 R3 复审指出的两组残留边界反例：
1. **隐藏与 ViewModel 重入发布保护（P1）**：
   - Presenter 在物理展示（`_window.Show()`）之前增加状态锁二次资格核验，准备期间若调用 `HideAsync`（`_latestOperation == null`）或被较新意图取代，绝不展示窗口并安全隐藏；
   - 彻底修复了对 `hasNewer` 的判断逻辑：明确区分“没有最新意图（Hide / Shutdown，`_latestOperation == null`）”与“确有较新意图（`_latestOperation != null && !ReferenceEquals(_latestOperation, op)`）”，防止将隐藏状态误判为有新意图而遗留可见窗口；
   - 成功路径与失败路径的可见性与激活快照均严格取自真实窗口属性（`_window.IsVisible` 与 `_window.IsActive`），杜绝以 `request.FocusInput` 伪造 `IsActive` 快照；
   - `TranslateWindowViewModel.ApplyRequest` 采用原子先提交状态、提取旧操作并在锁外撤销，再触发属性变更通知；通知执行期间若发生新意图 B 发布或窗口隐藏，旧 A 恢复执行后通过状态锁持锁校验会话归属。若已被抢占则安全退出返回 `false`，绝不 Detach 或 Cancel 新意图 B，绝不将 `_activeOperation` 改回 A。
2. **CTS 双向生命周期状态机（P1）**：
   - `QueuedCopyItem` 采用状态机模式与原子标志（`_writeDone` 与 `_cancelDone`），实现严格的双向等待生命周期：只有同时满足在途写入返回（`_writeDone == 1`）以及未取消或取消回调/注销已完全退出（`_cancelDone == 1`）时，才调用 `cts.Dispose()`；
   - 完美支持了“写入先返回 / 取消后退出”与“取消先退出 / 写入后返回”两条反向并发路径，彻底解决了取消回调先退出时剪贴板服务在途任务因 `token.WaitHandle` 提前释放而抛出 `ObjectDisposedException` 的问题；
   - 单一所有者在 `_copyGate` 锁内直接将 `cancelTcs` 加入 `_copyCancelTasks` 并登记 `_cancelingCtsSet`，杜绝任何 drain 误判空闲的竞态空档。
3. **正式回归与测试健壮性修复**：
   - 补齐了所有包含阻塞测试的 `finally` 闸门放行、`op.Dispose()` 释放与 `presenter.ShutdownAsync` 屏障等待，防止断言失败时遗留挂起任务；
   - 修复了 `WpfTestRunner.TeardownCoreAsync` 在首访时的 Dispatcher 异步等待问题，确保无 UI 测试用例也能干净退出。

## 四、关键问题修复与设计实现

### 4.1 隐藏与 ViewModel 重入发布保护（P1）

#### 根因分析
1. **准备期隐藏后展示失控**：
   在旧操作 A 执行 `TryShowAsync` 的定位与准备过程中，若外部调用了 `HideAsync`，`_latestOperation` 被清空为 `null`。旧逻辑在执行展示前未进行加锁资格检查，直接调用了 `_window.Show()`。随后的资格检查虽将 `accepted` 标记为 `false`，但因为 `hasNewer = !ReferenceEquals(_latestOperation, op)` 中 `_latestOperation` 为 `null` 时也被判定为 `hasNewer = true`，导致跳过了隐藏分支，窗口错误地保留在桌面上，且快照与实际均为可见。
2. **ViewModel 属性变更通知重入破坏新意图**：
   在旧操作 A 执行 `_viewModel.ApplyRequest` 时，设置 `InputText` 会同步触发 `PropertyChanged` 事件。如果监听该事件的外部逻辑立即通过公开端口发起新意图 B 的发布（`TryBeginOperation` + `TryShowAsync`），B 会成功发布并接管窗口与 ViewModel 会话（`_activeOperation = B`）。当通知栈解开并返回 A 时，旧 A 盲目继续执行后续的会话绑定逻辑，将新意图 B 的会话 Detach 并取消，且将 `_activeOperation` 强行改回失效的 A，导致 B 的操作所有权丢失。

#### 修复落地
1. **Show 之前的持锁资格复核与严格判空**：
   在 `TranslateWindowPresenter.TryShowAsync` 中，在调用 `_window!.Show()` 前加锁核验资格：
   ```csharp
   bool canShow = false;
   lock (_gate)
   {
       if (!_isShuttingDown && !op.IsCallerDisposed && !op.CancellationToken.IsCancellationRequested && ReferenceEquals(_latestOperation, op))
       {
           canShow = true;
       }
       else
       {
           accepted = false;
           bool hasNewer = !ReferenceEquals(_latestOperation, op) && _latestOperation != null;
           if (!hasNewer && !wasVisibleBefore)
           {
               _isVisibleSnapshot = false;
               _isActiveSnapshot = false;
           }
           else if (_latestOperation == null)
           {
               _isVisibleSnapshot = false;
               _isActiveSnapshot = false;
           }
           else
           {
               _isVisibleSnapshot = _window != null && _window.IsVisible;
               _isActiveSnapshot = _window != null && _window.IsActive;
           }
       }
   }

   if (!canShow)
   {
       if (_window != null && _window.IsVisible && _latestOperation == null)
       {
           try { _window.Hide(); } catch { }
       }
       return Task.CompletedTask;
   }
   ```
   若在准备期已调用 Hide（`_latestOperation == null`），`canShow` 为 `false`，绝不调用 `_window.Show()`；若窗口当前仍为可见则立即安全隐藏，且快照强制同步为 `false`。
2. **真实快照统一取自真实窗口属性**：
   无论在准备失败、ApplyRequest 失败还是发布成功路径，快照均严格根据真实窗口状态计算：
   ```csharp
   _isVisibleSnapshot = _window != null && _window.IsVisible;
   _isActiveSnapshot = _window != null && _window.IsActive;
   ```
   移除了成功路径中曾有的 `_isActiveSnapshot = request.FocusInput` 伪造快照。
3. **ViewModel 先原子提交再通知，通知后校验所有权**：
   `TranslateWindowViewModel.ApplyRequest` 改造为返回 `bool` 的防重入工作流：
   - 入口加锁：原子赋予 `_activeOperation = operation` 与 `operation.AttachSession()`，并提取 `oldOp`；
   - 锁外取消并分离 `oldOp`，确保不阻塞当前锁；
   - 触发 `InputText` 的 `OnPropertyChanged`；
   - 关键校验：通知返回后，立即加锁复核 `ReferenceEquals(_activeOperation, operation)` 与取消令牌状态。如果通知重入中已由新意图 B 接管（或被 Hide 撤销），旧 A 立即中止，返回 `false`，绝不修改当前已被新意图占有的 `_activeOperation`，绝不调用任何撤销或取消新 B 的逻辑。
4. **Presenter 处理 ApplyRequest 返回结果**：
   Presenter 在 `ApplyRequest` 返回后再次持锁复核，若 `applied == false` 或 `!ReferenceEquals(_latestOperation, op)`，确认操作已被取代，旧 A 仅取消自身，绝不回滚新意图的窗口。

### 4.2 CTS 双向等待写入与取消结束（P1）

#### 根因分析
在 R3 方案中，取消任务（`cancelTcs`）在 `CancelAsync()` 结束后即被判定为取消完成，并触发了 CTS 的 `Dispose()`。然而在反向时序下（取消回调先执行完毕并退出，但后台在途的剪贴板原生写入 `IClipboardService.SetTextAsync` 尚未返回），CTS 被提前释放，导致在途写入操作在后续访问 `token.WaitHandle` 或发生检查时抛出 `ObjectDisposedException`。

#### 修复落地
1. **QueuedCopyItem 引入双向原子完成状态机**：
   ```csharp
   private sealed class QueuedCopyItem
   {
       private int _writeDone;
       private int _cancelDone;
       private int _disposed;

       public string Text { get; }
       public CancellationTokenSource Cts { get; }
       public bool CancelRequested { get; set; }
       public bool IsCancelRegistered { get; set; }

       public QueuedCopyItem(string text, CancellationTokenSource cts)
       {
           Text = text;
           Cts = cts;
       }

       public void MarkWriteFinished()
       {
           Interlocked.Exchange(ref _writeDone, 1);
           TryDispose();
       }

       public void MarkCancelFinished()
       {
           Interlocked.Exchange(ref _cancelDone, 1);
           TryDispose();
       }

       public void TryDispose()
       {
           if (Volatile.Read(ref _writeDone) == 1)
           {
               if (!CancelRequested || Volatile.Read(ref _cancelDone) == 1)
               {
                   if (Interlocked.Exchange(ref _disposed, 1) == 0)
                   {
                       try { Cts.Dispose(); } catch { }
                   }
               }
           }
       }
   }
   ```
   - 规则 1：**写入未结束，CTS 绝不释放**。即使取消回调已完全执行退出（`_cancelDone == 1`），由于 `_writeDone == 0`，`TryDispose` 不执行释放，确保传给剪贴板服务的 `CancellationToken` 持续有效。
   - 规则 2：**若已请求取消，取消未完成前 CTS 绝不释放**。即使写入提前返回（`_writeDone == 1`），若 `CancelRequested` 为 true，必须等待 `_cancelDone == 1` 后才由取消工作线程执行释放。
   - 规则 3：**未启动的被替换待项明确标记写入完成**。当队列中的待办项被更新的复制请求替换并取消时，直接调用 `oldPending.MarkWriteFinished()`，其 CTS 仅在取消回调退出后由取消工作线程统一释放。
2. **单一所有者原子登记**：
   在 `_copyGate` 锁内原子加入 `_copyCancelTasks` 集合并登记 `_cancelingCtsSet`，彻底杜绝 drain 轮询误判空闲的任何缝隙。
