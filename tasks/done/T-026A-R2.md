## 2. R2-01：新 Show 后仅开始下一操作，不得由旧恢复隐藏新内容

独立程序在旧恢复的 Show 边界内依次执行：实际 TryShow 成功并可见 → TryBeginOperation 接纳下一操作（无 Hide/Close/下一次 Show）→ 返回旧恢复。R1 的 HasNewShow 要求 `_showVersion == _version`，把仅开始下一操作当作新显示不再受保护，旧恢复随后隐藏了新窗口。

```text
SHOW_THEN_PENDING entered=True accepted=True pendingAdmitted=True visibleBeforeOldShow=True finalVisible=False
```

同一程序对 SHA256 确认的初交 cb5981e 产品 DLL 对照，finalVisible=True；这是 R1 新引入的回退。修正后新 operation 仍须撤销截图准备，但不允许旧租约因此隐藏已经由较新成功 Show 接管的窗口。仅有新 operation、从未发生较新 Show 时，旧恢复仍须撤销，不能回退原 A 对照。

不能简单撤回 R1 的条件到历史 `_showVersion > version`，否则会重新引入 Show→Hide 后复活。保持 Show→Hide 隐藏、Hide→Show/仅 Show 保留；正常归还与 `_undoRestore` 失败重试采用一致的实际可见性归属。

## 3. R2-02：已失败并清理的新发布不得被旧恢复复活

在旧恢复的 Show 边界内，发起真实有效 TryShow，并只让外部 placement.SetWindowBounds 返回 false。TryShow 已返回 false，原失败清理后实际 Window 不可见；继续旧恢复却重新显示窗口。当前前移的 `AdvanceLocked(showing:true)` 既承担及时撤销，又被当作新展示成功，失败后没有收回对应可见性归属。

```text
FAILED_NEW_SHOW entered=True rejected=True hiddenBeforeOldShow=True finalVisible=True reason=DisplayIntent
```

修正后保留 R1-01：任何可能的原生显示/激活之前仍须锁外及时撤销旧准备。另正确结算本次显示尝试的成功/失败与其清理后的可见性，旧恢复不能把已失败并收好的窗口重新显示；不能通过延后通知、把 TryShow 失败改写为成功或跳过原发布清理解决。老尝试的失败也不能隐藏后来真正成功的展示。

这是仍未补齐的失败路径；cb5981e 同样会被旧恢复复活（当时 reason=None），不能把它误写为 R1 首次引入。
