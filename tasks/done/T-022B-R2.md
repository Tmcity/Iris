## 2. R2-01：原子上下文、迟到启动与最终取消

已复现：并发 Read 出现 NullReferenceException；Ready 超时后启动任务仍未返回，Read 已返回 TimedOut、第二次 Read 成功且 Stop 已完成；最终目标校验里取消后仍返回 Success；取消/Stop 导致 Kill 的真实退出码为 -1 时返回 Failed 而非取消。

1. 活动上下文发布之前创建完整、非空的执行完成屏障；不能先赋 `_activeOperation`、离锁后再填 `ExecutionTask`。Busy/Stop/Dispose 不读取尚未初始化的 Task。整个启动、读取、清理和失败重试期间由同一上下文持有资源，不因逻辑结果出现就让出活动槽。
2. 显式持有实际 Start Task 和迟到 session。禁止 `_ = CleanupDelayedStartAsync(...)` 后立即返回并清空活动槽，也不能 catch 所有异常后称“启动失败，无需收尾”。超时/取消只撤销逻辑请求；Read、Stop、DisposeAsync 必须等待实际启动结果及清理，或以可见清理失败保留责任，不能报告干净完成。迟到 session 不发送有效 Request；尚有责任时新 Read 不能被接纳。
3. 保持 Ready 1500ms 覆盖接纳/启动与握手、请求响应 300ms 分开且单调，不新增“超时后后台自清理就算完成”的例外。用 FakeTimeProvider 门闩验证启动晚于预算、取消启动、停止启动，以及迟到清理失败后的重试。
4. 最终目标校验返回之后，在本次操作的发布点同时复核调用方取消、Stop 与上下文身份。不能在校验之前只检查一次 CallerToken。取消/停止后的成功物理清理应保留取消语义，不能因本次主动 Kill 的非零退出码先返回 PROCESS_EXIT_UNEXPECTED；真实清理失败仍可见且保有资源。正常未取消的非零退出仍 Failed。
5. 完成真实资源收尾后配对释放每次 linked CTS / token registrations；现在 LinkedCts 无 Dispose，常驻 reader 会累计注册。安全映射启动/目标查询错误，不透传原始异常正文。

## 3. R2-02：所有入口共享清理、错误可见且后台执行

已复现：HasExited 抛错后首个 child 仍活着、Retry 不清理、新 Read 成功；Dispose 首次失败后并发两个 Retry 与 Stop 对同一 session 同时进入三次 Dispose；WPF Dispatcher 上 Retry 在 UI 执行 Dispose。实际 RealUiaProcessSession 会吞掉 stderr 任务故障，第二次 Dispose 在首次仍等待 stderr 时提前完成。

1. Read/Stop/RetryCleanup/Dispose 统一通过上下文中的清理协调器；失败后发起的新尝试也共享同一在途 Task，不绕过 `PerformCleanupAsync` 各调用 `DoCleanupSessionCoreAsync`。记住已经完成的退出/流/句柄阶段，重试只做尚未完成的责任。
2. HasExited、Kill、WaitForExit、stdout/stderr 排空与关闭、Process.Dispose 任一故障都不能跳过资源登记、在 finally 丢引用，或被后续成功状态覆盖。Stop 必须观察当前尝试中新产生的失败，不能只用进入时的旧快照。清理异常只含安全阶段/代码/HRESULT，不附带原始异常正文或协议内容。
3. 真实 runner/session 不用空 catch 把失败写成成功。明确正常 EOF/本次取消与意外 I/O 故障；stderr 的 Task 被持有、观察且完成到终态，不能只等待后吞掉错误。已启动 Process 在包装/管道初始化失败时也有回收责任。
4. `RealUiaProcessSession.DisposeAsync` 以完整共享屏障表示释放完成；不能先置 `_disposed=1` 再允许后续调用直接成功。每个流独立尝试清理，某个流关闭失败不阻止其它资源的释放。失败保留可重试阶段，不无限等待无人持有的 drain。
5. Stop/Retry/Dispose 的 Process、管道和释放工作也离开 UI；不要在持 `_gate` 时同步执行清理正文或外部取消回调。同步 Dispose 仍对活跃/失败未收尾状态明确失败，不阻塞。使用真实 WPF STA Dispatcher 测试 Stop/Retry/Dispose 的线程、可调度性与共享屏障；不只测 Read 的 StartAsync 线程。

## 4. R2-03：协议剩余边界

已复现：`status:"0"` 被解析为 Success 并返回文本；`status:"999"` 通过 codec；Reply 后真实读取错误 IOException 被 `IsCleanEof(ms)` 判成正常 EOF，父端仍发布 Success。

1. 以明确 wire 字面值/允许的宿主状态集合解析 Status，不用未校验的 Enum.TryParse 接受数值字符串、未定义值或组合名称。合法无选区/失败等状态保持正确映射；Ready/Request/Reply 必需字段、身份和 Text/ErrorCode 一致性继续独立校验。
2. 不能仅因尚未读到字节就把任意 IOException 当 EOF。正常零字节 EOF、经核实的平台管道正常关闭和意外读取失败应区分，意外失败不发布文本且收尾错误可见。同步宿主读与异步父端读均覆盖。
3. 保留 wire 总字节、CRLF、UTF-8、重复/截断/额外帧和文本预算成果。补测数值/未定义/组合 Status、坏字段、完整 Reply 后尾流故障；使用实际 codec 和 reader，直接构造坏 JSON，不能只测会修正输入的 SerializeReply。
4. 对齐错误码校验与报告：现有字符逐位白名单并不等于声明的 `[A-Z0-9_]` 或精确 HRESULT 格式。明确实际支持的安全代码/有界格式，统一 codec 与结果层；不允许原始 provider 内容作为错误码传出。

## 5. R2-04：真实 COM 错误分类、完整释放与选区预算

已复现：实际 RealUiaAutomationSession 的 GetFocusedElement 抛 E_FAIL 后 worker 返回 Unsupported / NO_FOCUSED_ELEMENT；实际 pattern 查询的断连错误被吞成 null。祖先释放首个失败后第二个未释放。65,535 字符后接空 range 被误判 TooLong，甚至未读取空 range。

1. 仅明确“不支持 pattern”条件走降级/Unsupported；焦点、parent、pattern 的其它 COM 错误安全映射 Failed。不能 catch 所有 COMException 转成无控件/无 pattern。保留 Pattern2 不支持时的经典降级与不读取全文的限制。
2. 所有自有 COM 包装对象、祖先、walker、array、partial ranges、pattern 和初始化失败对象逐项尝试释放。一个失败不跳过剩余对象，也不空 catch 假装成功；错误通过 worker 安全反映。保留 BSTR finally 释放及 range 数量在分配/枚举前的限制。

4. 空 range 不消耗分隔符预算。处理总长接近或达到 65,536、后续为空/退化/非空 range 的边界：先有界判断其实际内容，再决定分隔符和 TooLong；仍不得调用无界 GetText(-1)，保留有界剩余+1 策略。

## 2. 关键代码落地细节

### 2.1 R2-01：原子上下文、迟到启动与最终取消
- **预建非空执行完成屏障**：在 `UiaSelectionReader.cs` 中，`ReadOperationContext` 构造时立即创建并在持锁期间直接分配至 `_activeOperation`，彻底杜绝先赋值上下文再异步补充 Task 引发的并发 `NullReferenceException`。
- **迟到启动持有与责任锁定**：`op.StartTask` 显式持有底层进程启动 Task；在 Ready 预算超时或请求取消时，并不丢弃尚未返回的启动任务，而是 `await startTask` 捕获生成的 session，纳入 `SessionCleanupCoordinator` 进行物理终止与确认。清理未成功之前，保留失败协调器责任，阻止后续 Read 介入。
- **发布点三要素原子复核**：在最终前台窗口校验返回之后、结果发布给调用方之前的发布点，同时原子检查：1) 调用方 `CallerToken.ThrowIfCancellationRequested()`；2) `_isStopped`；3) 上下文身份 `_activeOperation == op`。对于因取消/停止而 Kill 的进程，即使平台报告非零退出码（-1），也正确尊重取消语义，不覆盖为意外退出错误。
- **成对释放 LinkedCts**：在 `ExecuteReadCoreAsync` 的 `finally` 块中严格释放本次操作创建的 `LinkedCts`，杜绝长生命周期 reader 累积 token 注册。

### 2.2 R2-02：所有入口共享清理、错误可见且离开 UI
- **统一协调器与共享屏障**：所有入口（Read 异常收尾、`StopAsync`、`RetryCleanupAsync`、`DisposeAsync`）统一路由至同一 `SessionCleanupCoordinator`，共享在途清理 Task，重试只执行尚未确认完成的责任阶段。
- **流任务持有与错误可见**：`RealUiaProcessSession` 显式持有 stderr drain 任务 `_stderrDrainTask`，在 `DoDisposeAsyncCore` 中观察并等待终态，不静默吞没错误。
- **独立流与句柄隔离释放**：`RealUiaProcessSession` 中 stdin、stdout、stderr、Process 各自独立在单独 `try-catch` 中尝试释放；若已关闭则安全捕获 `ObjectDisposedException` 并标记完成，不阻断其它流与进程句柄释放；未完全释放时允许重试。
- **后台执行物理清理**：`StopAsync` 与 `RetryCleanupAsync` 均调度至后台线程池执行，离开 WPF UI 线程，持锁期间绝不同步执行 native/管道释放或外部取消回调。

### 2.3 R2-03：协议剩余边界与错误码格式
- **Status Wire 字面量严格匹配**：`UiaProtocol.cs` 中舍弃宽松的 `Enum.TryParse`，改用显式白名单字符串 switch：仅接受 `"Success"`, `"Empty"`, `"Unsupported"`, `"Sensitive"`, `"TooLong"`, `"TargetChanged"`, `"Failed"`。任何数值型字符串（如 `"0"`, `"999"`）、小写字符串或未定义字面量一律抛出 `JsonException` 并在父端判定为格式损坏。
- **区分真实 EOF 与意外 I/O 故障**：引入 `UiaProtocolFrameReader.IsPipeClosedException`，区分正常平台管道关闭与意外读取 `IOException`，意外读取故障不发布 Success，收尾错误明确可见。
- **对齐错误码格式规范**：`UiaProtocolCodec.IsValidErrorCode` 与 `UiaSelectionResult.SanitizeErrorCode` 统一限定为安全错误代码：1-32 位大写英数字与下划线 `[A-Z0-9_]{1,32}` 或精确 COM HRESULT 格式（`COM_0x[0-9A-Fa-f]{8}` / `0x[0-9A-Fa-f]{8}`）；不合规内容一律脱敏为 `"INVALID_ERROR_CODE"`，杜绝 provider 原始不可信文本外泄。

### 2.4 R2-04：COM 错误分类、生命周期与选区预算
- **显式 MTA 线程生命周期**：在 `NativeMethods.txt` 中引入 `CoInitializeEx` / `CoUninitialize`。`RealNativeUiaAdapter.CreateSession` 验证当前线程为 MTA 后调用 `CoInitializeEx(COINIT_MULTITHREADED)` 并绑定创建线程 ID；`RealUiaAutomationSession.Dispose` 强制在同线程配对调用 `CoUninitialize()`。
- **COM 错误精确分类**：仅在 explicit `0x80040204`（`UIA_E_NOTSUPPORTED`）或 `E_NOTIMPL`/`E_NOINTERFACE` 时降级至经典 `TextPattern` 或上报 `Unsupported`；焦点获取、祖先查询、断开连接等其它 COMException 均安全映射为 `Failed`（或错误向上传播），绝不泛吞成 null。
- **逐项安全隔离释放**：`UiaSelectionWorker.IsElementFromExpectedSource` 遍历祖先链时，逐个在独立 `try-catch` 中释放元素，前一个释放失败仍继续释放后续元素，并标记失败通知上层；`FakeUiaTextPattern` 与 `FakeUiaTextRange` 针对托管/COM 替身提供释放验证。
- **空 Range 预算保护**：在遍历 range 时，先有界预判其实际文本内容；空/退化 range 不消耗 `\n` 分隔符预算，处理总长接近 65,536 时后续接空 range 不被误判为 `TooLong`。
