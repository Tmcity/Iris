## 2. R2-01：初始化真实结束与原生/通知收尾

### 修复要求

1. 区分“调用方已取消/逻辑结果已完成”“初始化线程真实结束”“资源清理真实完成”。不能用可提前取消的 initTcs.Task 充当物理初始化屏障。初始化完整登记句柄/线程、报告成功或失败后，清理才可判断资源为空和释放 active owner。

3. 真正检查 PostThreadQuitMessage 的 bool 返回。失败应形成可见、可重试的故障，保留线程/委托；不能继续等待永远不会收到的退出消息。GetMessage=-1 与异常不能仅 break/log：撤销捕获、产生安全失败结果、启动并观察实际收尾；非正常 0 返回也不得留下未完成会话。
4. 保持已卸载、线程已退出、回调已退出、通知 worker 已退出等阶段状态；重复/并发停止共享在途工作，失败重试不重复卸载旧句柄。持有并等待 RunProgressWorkerAsync，不仅 TryComplete channel。
5. native 回调只做有界状态/终态发布，不同步执行 native 卸载、等待 CancellationTokenRegistration.Dispose 或完整收尾。保持异常边界，不让 fallback CallNext 的异常再次逸出；委托根在回调与线程真实退出后才释放。

## 3. R2-02：失败停止、用户重试与普通关闭

### 已复现

录入清理失败后 HasFailedCleanup 为 true，但 StopAsync 等待只在成功时才完成的 context.CompletionTask，始终不返回错误。真实页面的重试命令虽 CanExecute=true，按钮仍 Collapsed。调用普通 window.Close 时，清理闸门尚未放行，窗口已消失且 session.IsOpen=false；R1 只测 session.ShutdownAsync 没覆盖此入口。

### 修复要求

1. context 的本次运行/清理尝试必须可观察成功或失败；失败保留资源，不把等待者挂在一个只有未来人工修复才完成的 Task 上。Cancel、Stop、窗口关闭和 AppBootstrapper 应收到本次清理失败并退出本次请求，允许重试。

3. Begin 失败且未返回 session 时，控制器仍调用并等待服务 StopAsync 的真实回滚；回滚失败保留 pause，不得恢复系统注册。停止准备中的 Record 时保留已开始前置工作跟踪，不为录入取消用户翻译。
4. 普通 X、取消关闭与 session/presenter shutdown 使用同一异步关闭协议：先取消并 drain，成功后才真正关闭 HWND 与释放 scope；失败保持窗口可用、scope 存活，并展示可点击的重试。不能依赖 Closed 之后补等，不能用 ForceClose 绕过被测入口。

## 二、核心实现要点

### 2.1 原生初始化与线程/通知收尾 (R2-01)
- **解耦物理初始化与逻辑 TCS**：`HotkeyCaptureService` 与 `HotkeyCaptureSession` 不再将可提前取消的逻辑 TCS 作为物理屏障，引入真正的物理初始化屏障 `_initCompleted` 与 `_nativeHandleSet`。即使 `BeginAsync` 被取消或发生异常，也必须等待消息循环与线程真实退出、物理卸载完成（`UnhookWindowsHookEx`）后方可释放所有权与接纳新会话。
- **PostThreadQuitMessage 检查与消息循环异常收尾**：显式检查 `PostThreadQuitMessage` 的 `bool` 返回值；当返回 false 或遇到 `GetMessage = -1` 错误时，主动向当前 session 发布失败终态并驱动内部收尾，杜绝永久挂起死等退出消息。
- **通知 Worker 真实等待与回调异常守护**：`DisposeAsync` 与内部清理持有并等待 `RunProgressWorkerAsync` 任务完全退出；native 回调内仅做有界轻量状态发布，不执行重量级清理或外部取消回调；守护 fallback `CallNextHookEx` 的异常边界。
- **按键释放跟踪修复**：准备期新按下的键纳入等待释放集合，修正了“准备期按 A 只松 Enter 即断言 Ready”的测试缺陷。

### 2.2 失败停止、重试与普通关闭 (R2-02)
- **消除清理失败死等**：`ActiveRecordingContext.SetCleanupFailed` 在清理失败时直接使 `_completionTcs` 处于 Faulted 状态，使 `StopAsync`、`CancelRecordingAsync` 及关窗流程能立即观察到本次清理失败，消除挂起死等。
- **统一异步关窗协议与 HWND/Scope 存活**：`SettingsWindowSession.OnWindowClosing` 针对普通关闭（点 X 或 `window.Close()`）进行拦截（`e.Cancel = true`）：仅当存在活跃录入、清理失败未重试、正在保存或已有在途清理时拦截立即销毁，触发异步排干；排干失败（如录入清理失败）时保持 HWND 存活、保留 DI scope，界面展示“重试快捷键应用”按钮；重试成功后再次关窗则安全退出并释放。
- **可操作 UI 按钮**：`SettingsWindow.xaml` 快捷键设置页面父 StackPanel 绑定 `IsEnabled="{Binding CanAccessHotkeysTab}"`，录入中仅冻结快捷键编辑，“取消录入”按钮保持可用；重试按钮同时绑定 `CanRetryHotkeysOrCleanup`，覆盖 `HasFailedRecordingCleanup`。
- **Host 退出收尾**：`AppBootstrapper` 在退出时撤销热键准入，按正确依赖顺序先关停录入控制器与 native，再沿用 Presenter/Host 顺序；移除了同步退出中阻塞 UI 线程的 `DisposeAsync().AsTask().GetAwaiter().GetResult()`。

### 2.3 保存恢复 UI 线程、录入身份与配置消费 (R2-03)
- **保存显式回 UI 线程**：`SettingsViewModel.ExecuteSaveAsync` 在等待录入排干与安全校验后，显式通过 `_uiDispatcher.InvokeAsync` 切换回 UI 线程执行 `BeforeSave`、未失焦草稿刷新与保存安全屏障。
- **录入代次校验**：引入 `_recordingSessionSeq` 代次递增机制，在同一 HotkeyItem 重复开启录入时，丢弃旧录入会话已排队的进度通知。
- **配置消费者代次配对**：`HotkeyCoordinator` 引入 `_processingGeneration` 代次配对机制，消除暂停与恢复交错导致 `_isProcessingSettings` 永久为 true 的死锁缺陷；`StopAcceptanceAndNativeAsync` 与 `StopSynchronousFallback` 显式重置代次。

### 2.4 可读布局与双主题完全隔离证据 (R2-04)
- **布局无裁切**：调整 `SettingsWindow.xaml` 中 `HotkeyRecorderBox` 布局（MinWidth="360" MaxWidth="500"），即使在 600x440 最小窗口下，长组合 `"Ctrl+Alt+Shift+Win+F10"` 的主键 F10 绝不被裁切，取消/重试按钮完整可见。
- **W04 显式窗口主题字典隔离**：W04 针对 8 组（浅色/深色 × 默认/最小尺寸 × 100%/150% 缩放）离屏渲染，直接向窗口注入主题字典，彻底隔离测试套件间的静态主题字典残留，8 组 PNG 截图全部生成且 SHA256 哈希全部互不相同，深浅主题样式鲜明分离。
