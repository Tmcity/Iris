## 1. 背景

到目前为止，Iris.App 还是 WPF 模板自带的一个空窗口。本工单把它改造成真正的常驻托盘程序：单实例运行、没有主窗口、由 Generic Host 组装全部服务、有托盘图标与通知、能跟随设置切换主题与日志级别、任何未处理异常都会被记录而不会让进程崩溃。完成后，M0 基础设施里程碑结束。

本工单同时处理两批遗留问题：**T-002 评审遗留的 5 项**（BACKLOG 中 T-005 名下），以及 **T-004 评审发现的 3 项代码质量问题**（第 6.8 节）。

启动与退出的全部细节已写进 **ARCH v1.5 §10.1.1**。本工单严格按该节实现；工单中不再重复的内容，一律以该节为准。

## 2. 目标

1. `Program.Main` + 单实例锁 + 致命错误对话框，失败路径在构造任何 WPF 对象之前退出。
2. Generic Host 组合根（`AppHostBuilder`），Serilog 为唯一日志提供程序，容器启用构建时校验。
3. `AppBootstrapper` 启动与退出序列（ARCH §10.1 的第 1、2、3、8 步；第 4–7、9 步留 TODO）。
4. 托盘图标、托盘通知、主题、日志级别随设置变化、全局异常处理。
5. T-002 / T-004 遗留项。

### 6.2 Platform.Windows：SingleInstanceGuard 与 FatalErrorDialog

```csharp
namespace Iris.Platform.Windows.SystemIntegration;

public sealed class SingleInstanceGuard : IDisposable
{
    /// <summary>名称 = IpcConstants.MutexNamePrefix + 当前用户 SID。已有实例时返回 null。</summary>
    public static SingleInstanceGuard? TryAcquireForCurrentUser();

    /// <summary>测试用：指定完整的 Mutex 名称。</summary>
    internal static SingleInstanceGuard? TryAcquire(string mutexName);

    /// <summary>释放并关闭 Mutex。必须在调用 TryAcquire 的同一线程上调用；重复调用无副作用。</summary>
    public void Dispose();
}

public static class FatalErrorDialog
{
    /// <summary>置顶的错误对话框（Win32 MessageBoxW：MB_OK | MB_ICONERROR | MB_TOPMOST | MB_SETFOREGROUND），阻塞直到用户关闭。</summary>
    public static void Show(string title, string message);
}
```
- SID：`WindowsIdentity.GetCurrent().User!.Value`。
- 获取逻辑严格按 ARCH §10.1.1（`initiallyOwned: false` + `WaitOne(0)` + 捕获 `AbandonedMutexException`）。
- `FatalErrorDialog` 通过 CsWin32 生成 P/Invoke（`NativeMethods.txt` 中加入 `MessageBox`）。
- 这两个类型是 Platform.Windows 中**仅有的两个 public 实现类型**（它们在 DI 容器建立之前就要被使用）。

### 6.3 Program.Main

严格按 ARCH §10.1.1 的 5 个步骤实现。补充要求：
- 签名：`[STAThread] public static int Main(string[] args)`，放在 `internal static class Program` 中。

### 6.5 App、AppBootstrapper、AppLifetime

- `App`：由 DI 构造，构造函数参数为 `AppBootstrapper` 与 `GlobalExceptionHandler`；构造函数中设置 `ShutdownMode = OnExplicitShutdown`，并调用 `GlobalExceptionHandler.Install(this)`。重写 `OnStartup`（`async void`，整体 try/catch → 记 Fatal → `FatalErrorDialog` → `Shutdown(1)`），调用 `bootstrapper.StartAsync()`；重写 `OnExit`，调用 `bootstrapper.StopSynchronousParts()`（幂等的同步清理）。
- `AppBootstrapper.StartAsync()`：严格按 ARCH §10.1.1 的 7 个步骤；第 4–7、9 步的 ARCH §10.1 功能留 `// TODO(T-0xx)`。日志使用注入的 `ILogger<AppBootstrapper>`（**T2-3**：日志行带 SourceContext）。
- `AppBootstrapper.StopAsync()`：严格按 ARCH §10.1.1 的退出序列，幂等（用 `Interlocked.Exchange` 标志位）。
- `AppLifetime.RequestShutdown()`：`Application.Current.Dispatcher.InvokeAsync(() => bootstrapper.StopAsync())`，可以从任意线程调用。

### 6.6 托盘、通知、主题、日志级别

- **TrayIconController**：用 H.NotifyIcon.Wpf 在代码中创建 `TaskbarIcon`（ToolTip 为 `Iris`，图标取自 `Resources/Icons/iris.ico`）。在代码中创建时需要调用 `ForceCreate()`，以所装版本的文档为准。右键菜单：
  - `设置…`（置灰，`// TODO(T-018)`）
  - 分隔线
  - 仅 DEBUG 构建（`#if DEBUG`）：`调试：UI 线程异常`、`调试：后台任务异常`（抛出后立即 `GC.Collect(); GC.WaitForPendingFinalizers();`，让未观察的异常尽快触发）、`调试：切换主题`（依次切换 System → Light → Dark，通过 `ISettingsService.UpdateAsync` 修改设置，**不要**直接调用 ThemeService）
  - `退出` → `IAppLifetime.RequestShutdown()`
  - 实现 `IDisposable`，由 `AppBootstrapper` 在退出时释放。
- **TrayNotificationService**：按 ARCH §10.1.1 实现排队；`Notify` 可以从任意线程调用（用 `Dispatcher.InvokeAsync` 切换线程）；`NotificationLevel` 映射到 H.NotifyIcon 的通知图标（Info / Success → Info，Warning → Warning，Error → Error）。提供 `internal void AttachTray(TrayIconController tray)`，调用后输出队列中的通知。
- **ThemeService**：`Apply(AppTheme theme)`。Light / Dark 调用 WPF-UI 的主题管理器；System 读取系统当前主题后应用，并订阅 `Microsoft.Win32.SystemEvents.UserPreferenceChanged`（切换到其他模式时取消订阅；实现 `IDisposable`，因为 `SystemEvents` 是静态事件，不取消订阅会造成泄漏）。必须在 UI 线程执行。
- **LogLevelController**（**T2-2**）：订阅 `ISettingsService.Changed`，用 `IrisLogging.TryParseLevel` 解析 `General.LogLevel` 后设置 `LoggingLevelSwitch.MinimumLevel`；解析失败时保持当前值并记 Warning。提供 `ApplyCurrent()`，供启动流程在设置加载后调用。
- **IrisLogging.CreateLogger**（**T2-2**）：删除 `levelSwitch.MinimumLevel = LogEventLevel.Information;` 这一行；不再修改调用方传入的对象。

### 6.7 全局异常与限流

- **GlobalExceptionHandler**：严格按 ARCH §10.1.1。`Install(Application app)` 只能调用一次；实现 `IDisposable`，释放时取消三个事件的订阅。
- **NotificationThrottle**：`bool TryAcquire()`，按注入的 `TimeProvider` 判断，每 10 秒最多返回一次 true。纯逻辑，单独测试。

### 6.8 T-004 评审遗留（代码质量）

- **C4-1**：`DpapiSecretStore.LoadInitial` 与 `ReloadUnderLock` 约 50 行几乎完全相同。合并为一个私有方法（例如 `LoadFromDisk()`）；两者唯一的差异——构造时读取失败要清空字典，重新加载时读取失败保留字典——用一个参数表达。
- **C4-2**：“共享冲突重试 + `IsTransient` 判断”目前有三份拷贝（`AtomicFile`、`JsonSettingsService.ReadFileWithRetryAsync`、`DpapiSecretStore.ReadFileWithRetry`）。在 `AtomicFile` 中新增 public 方法 `ReadAllBytes(string path)` 与 `ReadAllBytesAsync(string path, CancellationToken)`（与现有方法使用相同的重试策略；失败抛 `IrisException(StorageFailure, detail: path)`），并替换掉另外两处拷贝。
  - 注意：`JsonSettingsService` 原来读取的是文本（带 BOM 检测）。改为读取字节后，用 `new StreamReader(new MemoryStream(bytes), Encoding.UTF8, detectEncodingFromByteOrderMarks: true)` 解码，保证 L10（带 BOM 的文件）仍然通过。
  - 注意：各调用方原有的异常语义保持不变。设置服务读取失败 → 抛 `StorageFailure`；密钥存储读取失败 → 进入降级模式，这里要改为捕获 `IrisException`。
- **C4-3**：`S14` 在同一线程上调用 Get / Set，而 `System.Threading.Lock` 允许同一线程重入，所以这个测试无论事件是否在锁内触发都会通过，没有测到它想测的内容。改写为：在 `Changed` 处理器中，用 `Task.Run(() => store.Get(key)).Wait(TimeSpan.FromSeconds(5))` 从**另一个线程**读取，并断言返回 true。如果事件是在锁内触发的，另一个线程会一直拿不到锁，`Wait` 返回 false，测试失败。改写后，临时把 `FireChanged` 挪到锁内确认测试变红，然后恢复（在报告中说明）。

### 11.6 与工单的偏差及 API 差异记录
1. **`App.xaml` 入口移除**：
   - 工单 6.1 提及 `<ApplicationDefinition Remove="App.xaml" />` 与 `<Page Include="App.xaml" />`。在 .NET 10 SDK WPF 构建管道中，该配置成功移除了 `App.g.cs` 中的 `Main` 方法生成，完全符合“编译后只存在 `Program.Main` 一个入口”的要求。
2. **`App` 类构造器可见性与 `ValidateOnBuild`**：
   - WPF 默认生成的 `App` 在 XAML 编译后属于公共分部类，但其构造函数需为 public 供 DI 容器在 `ValidateOnBuild = true` 时通过反射分析参数。
   - 解决方案：在 `App.xaml` 中指定 `x:ClassModifier="internal"`，在 `App.xaml.cs` 中声明 `internal partial class App` 并定义 `public App(...)` 构造器，既满足了容器静态验证，又保持了程序集内部封装。
3. **`H.NotifyIcon` 的无桌面/锁屏防御处理**：
   - Win32 API `Shell_NotifyIcon` 在系统无活跃桌面（如无 `Shell_TrayWnd`、自动化环境或锁屏）时会返回 `E_FAIL (0x80004005)`，导致 `H.NotifyIcon.Core.TrayIcon.Create()` 抛出 `InvalidOperationException: TryCreate failed`。
   - 解决方案：在 `TrayIconController` 的 `Initialize()` 及 `ShowNotification()` 中对此异常进行了防御性捕获；当 Explorer 恢复就绪后，`H.NotifyIcon` 注册的 `TaskbarCreated` 消息回调会自动补创托盘图标，保证无交互环境下进程平稳运行不崩溃。
