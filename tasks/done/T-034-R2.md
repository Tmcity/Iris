## 2. R2-1：验证实际结构，而非名称/关键字

当前实现仍只取列名，触发器/FTS 仅用 Contains 判断，索引只核对名称。以下错误结构会被当作正常 V2：

- 同名删除触发器执行 `DELETE FROM history_fts`，缺少按 old.id 限定；删除一条历史会抹掉其它记录的全文索引。
- 普通 history_fts 表加上名为 fts5/trigram 的列，能通过字符串包含检查。
- translation_history.id 改为 TEXT PRIMARY KEY，列名相同便被接受。

使用 SQLite 结构元数据和受支持 DDL 的严格判定验证关键列类型、主键/行号语义、外键目标及级联、FTS5 虚表/tokenizer、触发器事件/目标/删除谓词、索引归属及列顺序。允许固定支持本项目 V1/V2，不需要通用 SQL 解析框架；但不能以“字符串含有这些词”代替验证。格式差异可规范化，不能让注释、额外无关列或错误谓词伪装成正确结构。

可采用的最小方案：通过 table_info/table_list/index_list/index_xinfo 等元数据比对本项目预期结构；触发器和 FTS 声明与受支持的标准定义规范化后比较，拒绝缺失谓词或多余删除语句。不要通过在用户库上试执行破坏性操作来验证结构。

不兼容结构必须在持久化修改前安全拒绝，不能为了让校验通过自动修补未知库。

## 3. R2-2：写阶段再次确认版本与适用性

只读预检之后，实际读写连接重新取得的 user_version 目前没有再次验证。受控探针将预检后的 V2 推进到 99，初始化却成功并切到 WAL。

写阶段必须针对实际看到的版本验证支持范围和结构适用性，再执行 WAL/迁移；不能假定早先只读检查永远有效。仅支持明确的版本 0、1、2，不支持的值安全失败。迁移事务开始后也应避免使用过期的版本决策重复建表或错误升级。

用受控连接工厂在只读预检完成后、读写连接返回前改变版本或结构；断言拒绝，不发生本初始化器引入的 WAL/DDL/版本修改。保留合法 V1→V2、新库和并发初始化回归。

## 4. R2-3：提交前取消优先

当前在连接已打开后取消令牌、随后遇到外部写锁时，操作仍等待锁并返回 IrisException(StorageFailure)。R1 已要求取消优先，不能将这类操作报告成存储失败。

- 在进入下一项不可取消同步 I/O 前以及批量插入循环中检查令牌；尤其连接打开后、BeginTransaction 前应观察取消。
- 操作尚未提交且令牌已取消时，错误出口优先抛 OCE，完成回滚/释放；覆盖安全 IrisException、SqliteException 和其它存储失败分支。
- 提交成功后仍保持既定结果，不因迟到取消伪报失败。不得重新引入原始异常链。

测试以真实临时 SQLite 写锁与连接回调建立“打开成功 → 取消 → 事务锁冲突”的确定顺序；另覆盖批量写入中取消与成功提交后的迟到取消。不能只用调用前已取消的令牌代替。

## 2. 报告真实性与技术规范更正

依据工单 R2-5 要求，对原 R1 报告中的不准确描述作如下明确更正：

1. **结构校验与列信息更正**：
   - 原 R1 提交（`9ffa57a`）的 `GetTableColumns` 实际仅提取了列名集合（`HashSet<string>`），原报告“全部关键列与类型已校验”与代码事实不符。
   - 本次 R2 已实现完整的 `TableColumnInfo` 结构校验，对列名、列类型、NOT NULL、主键序号以及总列数均进行了严格比对。
2. **方法名称更正**：
   - 原 R1 报告提及 `WrapStorageException` 与 `TrimHistoryIfNeeded`。实际上代码中并没有这两个独立命名的私有方法，而是各操作内部的内联 catch 处理以及 `TrimNonFavorites` 方法。
3. **门闩等待方式更正**：
   - 原 R1 报告声称写门闩调用了 `WaitAsync`。实际上仓储操作被调度至后台线程池（`Task.Run`）执行，内部调用的是 `_writeLock.Wait(cancellationToken)` 同步阻塞，并非异步 `WaitAsync`。
4. **参数异常类型更正**：
   - 原 R1 报告声称非正 Id 抛出 `ValidationFailed` 错误。实际上代码执行的是参数前置检查 `if (id <= 0) throw new ArgumentOutOfRangeException(...)`，项目并不存在名为 `ValidationFailed` 的自定义错误枚举或异常类型。
