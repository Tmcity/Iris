## 1. 范围与实施要点

严格限制在原 T-019A 范围的取消提交点、回执/屏障和输入/草稿边界修复，未修改任何公共契约签名，未修改 App/T-018，不实现 OCR Registry，未引入新包，无真实联网。

### 1.1 R1-1：取消一直有效到真正提交
- `SettingsEditCoordinator.CommitAsync` 将有效 `cancellationToken` 传递给 `_settingsService.UpdateAsync`。
- 仅在 `UpdateAsync` 正常成功返回后，达成提交点（Commit Point）并切换到提交后阶段；后续观察者刷新与清理阶段忽略 caller 的迟到取消。
- `UpdateAsync` 发生提交前取消时（抛出 `OperationCanceledException`），先调用 `RollbackStagedCredentialsAsync` 尽力回收本次仍无引用的暂存凭据，再重新抛出 OCE，不转为 `StorageFailure`。

### 1.2 R1-2：回执记录观察者阶段，纯排序走屏障
- `SettingsApplyReceipt` 增加 `ObserversCompleted` 状态：
  `IsComplete => ObserversCompleted && RemainingCandidateSetIds.Count == 0 && RemainingCandidateLegacyProfileIds.Count == 0`。
- 零候选提交若观察者刷新失败，回执标记未完成并返回 `ApplyPending`；`RetryApplyAsync` 再次执行观察者刷新，成功后才标记完成。
- 纯 `TranslationOrderChange` 提交不跳过观察者屏障：仅当 `capturedPlan.TranslationChanges.Count == 0 && capturedPlan.TranslationOrder == null` 时才跳过屏障。

### 1.3 R1-3：统一并严格校验输入及默认 Options
- 严格校验 `CredentialEditKind` 和 `TranslationProfileChangeKind` 的 `Enum.IsDefined`。非法值（如 999）直接拒绝并返回 `ErrorCode.InvalidArgument`，绝不走 Clear 路径。
- 拒绝 null changes、null 凭据意图及包含 null 元素的列表结构，明确返回安全错误 `InvalidArgument`。
- 深度克隆与捕获阶段按 Kind 补齐默认 Options（Anthropic 默认 Effort="low"）；若模型包含 "haiku"，严格要求 Effort 必须为 null，否则拒绝为 `InvalidArgument`。

### 1.4 R1-4 & R1-5：草稿操作按意图、当前基线和操作类型准入
- `Keep` 模式下在短串行锁（`_gate`）内比对 `BaseProfile` 与当前配置（`IsProfileDeepEqual`），过期或被删除返回冲突错误；凭据解析（`ProviderCredentialResolver.Resolve`）移至后台线程（`Task.Run`）执行，不阻塞调用线程。
- 校验超时范围（5–600 秒）；已有服务的 `Replace`/`Clear` 测试使用独立凭据，不受基线旧坏引用阻断；新服务草稿仍不得任意指定持久引用。
- `TestDraftAsync` 捕获瞬态创建/工厂异常并封装为 `ProviderTestResult`，不让 `IrisException` 外漏；caller 取消按契约抛出 OCE。
- 租约在 Provider 实际工作退出后于 `finally` 块中释放。
