## 一、实施概况与缺陷修复

严格在 T-021-R1 规定范围内修复两个缺陷，不扩大范围，保留全部已有成果（四事件顺序、反向补偿、责任保留、脱敏日志、C20B-1 维护等）：

### 1. R1-01：原生调用彻底离开 UI 线程
- **原因分析**：原代码在 `CopyAsync` 入口直接内联调用 `RunCopyWorkflowAsync`，方法首行依赖 `await Task.Yield()`。当调用方处于 WPF STA 线程且配置了 `DispatcherSynchronizationContext` 时，`Task.Yield()` 会将续体 post 回原 UI 线程调度。在按键已释放场景下，由于无需等待（未触发 `Task.Delay`），所有原生调用（`GetAsyncKeyState`、`GetForegroundWindow`、`GetWindowThreadProcessId`、`IsWindow`、`SendInput`）均直接在 UI 线程同步运行。
- **修复方案**：
  - 在 `CopyAsync`、`RetryCleanupAsync`、`StopAsync` 中，严格在同步准入锁内完成状态检查与活动任务登记（`_activeCopyTask`、`_activeCleanupTask`、`_activeStopTask`），随后通过 `Task.Run(..., CancellationToken.None)` 明确将底层异步工作流（`RunCopyWorkflowAsync`、`RunCleanupWorkflowAsync`、`RunStopWorkflowAsync`）直接派发至 .NET 线程池后台线程。
  - 彻底移除三个工作流方法顶部的 `await Task.Yield();`，确保工作流从首行起即在后台运行，不捕获或回流到任何 UI `SynchronizationContext`。
  - `CopyAsync` 返回的 `copyTask` 完整覆盖实际 native 调用、补偿与自有 `finally` 收尾。

### 2. R1-02：最后目标查询后重新确认取消与停止
- **原因分析**：原 `ExecuteCopyCoreAsync` 中对 `token.ThrowIfCancellationRequested()` 的检查位于最终键状态与前台目标复核（`IsTargetValidAndForeground`）之前。在该最后一次原生目标查询期间，若发生外部 caller 取消或 `StopAsync()` 调用，此时 `SendInput` 尚未开始（`sendsAtRevocation = 0`），但查询返回后代码直接进入 `ExecuteSendSequence`，导致仍注入 4 个按键并返回 `Injected`。
- **修复方案**：
  - 在最后一次可能阻塞的原生目标与按键状态查询完成后、在正式发起第一个 `SendInput`（`ExecuteSendSequence`）之前，立即重新复核取消与停止状态：
    ```csharp
    lock (_syncRoot)
    {
        if (_isStopped)
        {
            throw new OperationCanceledException(token);
        }
    }

    token.ThrowIfCancellationRequested();
    ```
  - 若在此确定性窗口内取消或停止，立即抛出 `OperationCanceledException`，不执行任何 `SendInput` 调用（`totalSends = 0`），按键未按下（`HasPendingRelease == false`），并顺畅完成 `StopAsync` 的在途任务等待与收尾。
  - 严格保留提交点语义：首个 `SendInput` 开始后，晚到的取消不再丢弃释放责任，完整执行应有的 `KeyUp` 收尾。
